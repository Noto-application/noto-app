# RFC-008: Spec-Driven + Test-First разработка

**Статус:** Superseded by [ADR-013](../adr/013-spec-driven-development.md)
**Дата:** 2026-07-22

> Решение принято и вынесено в [ADR-013](../adr/013-spec-driven-development.md).
> Этот RFC оставлен как история проработки.

## Контекст

В проекте активно используются AI-ассистенты (Claude Code, Cursor, Codex). Их
слабое место — додумывание деталей, которых нет в задаче: агент заполняет
пробелы догадками, и результат расходится с задумкой.

На созвоне и в обсуждении команда согласилась использовать AI и задать ему
одинаковый вектор через Context Engineering (AGENTS.md, документация). Этот RFC
предлагает процесс работы над фичей, который снижает додумывание и делает
поведение проверяемым.

## Предложение

Микс двух практик:

1. **Spec-Driven Development** — значимая фича сначала описывается в
   спецификации: цель, контракт, поведение, крайние случаи. Спека живёт **рядом
   с кодом** (`<name>.spec.md` в папке модуля/слайса); `docs/specs/` держит
   реестр и кросс-модульные спеки.
2. **Test-First** — по спецификации сначала пишутся тесты (крайние случаи
   становятся тест-кейсами), затем код, закрывающий тесты.

Порядок для значимой фичи: **spec → тесты → код**.

Spec и тест — две рамки для AI: spec задаёт намерение словами, тест фиксирует
его исполняемо. Агент не может «переинтерпретировать» проверяемое поведение.

## Градация строгости

Полный цикл на каждую мелочь команда не выдержит — процесс привязан к масштабу.

| Масштаб                   | Процесс                                        |
| ------------------------- | ---------------------------------------------- |
| Значимая фича             | Spec → тесты → код; spec ревьюят перед стартом |
| Обычный модуль / эндпоинт | Тест-первым; spec — пара строк в описании PR   |
| Багфикс, вёрстка, мелочь  | Тест где осмысленно; spec не нужен             |

## Где test-first не применяем догматично

- **UI и вёрстка.** Тест-первым — на логику (хуки, стор, обработка данных), не
  на разметку. Визуал — Storybook + Playwright постфактум.
- **Realtime / Yjs.** Поведение CRDT эмерджентное; spec есть, тесты
  интеграционные и пишутся после спайка.
- **Внешние интеграции** (OpenAI, S3, TG-бот). Сначала спайк-прототип, тесты на
  обёртку потом — иначе тестируется собственный мок.

## Связь с существующими решениями

- **Contract-first ([RFC-001](./001-api-contract.md)).** ts-rest контракты в
  `packages/shared` — это уже спецификация API. Поток складывается: контракт →
  тест на хендлер → реализация. Не отдельная сущность.
- **Границы состояния ([ADR-005](../adr/005-state-management.md)).** Раздел
  «Взаимодействия» в спеке сверяется с матрицей состояния.
- **AGENTS.md.** Процесс кратко закреплён там, в разделе «Порядок работы над
  фичей».

## Риски

- **Overfitting тестов AI.** Если один агент за один проход пишет и тест, и код,
  он подгонит одно под другое — тест станет тавтологией. Правило: тест ревьюит
  человек до написания кода (либо тест и код — разные проходы).
- **Spec как второй код.** Если spec пересказывает реализацию прозой, работа
  дублируется. Spec — про поведение и контракт, не про реализацию.
- **Усталость от процесса.** Смягчается градацией: полный цикл только для
  значимых фич.

## Открытые вопросы

- Где проходит граница «значимой фичи» — договориться на примерах команды.
- Нужен ли обязательный ревью спеки отдельным человеком до старта, или
  достаточно самопроверки.
- Порог покрытия тестами (если вводим) — отдельно.
- Co-location vs `docs/specs/`: принято гибрид — спека рядом с кодом
  (`<name>.spec.md`), централизованно только реестр и кросс-модульные спеки.
  Проверить на практике, что реестр не рассинхронивается.

## Следующие шаги

1. Обсудить на командном созвоне.
2. При согласии — перевести в ADR и закрепить как обязательный процесс.
3. Обкатать на первой значимой фиче (кандидат — auth, BE-2/BE-3).
