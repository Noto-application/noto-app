# ADR-010: Task runner — Turborepo

**Статус:** Accepted  
**Дата:** 2026-07-21

## Контекст

[ADR-001](./001-monorepo-structure.md) зафиксировал monorepo на pnpm workspaces,
но не определил, чем запускать задачи в пакетах.

К моменту scaffold'а (BE-1) появились три пакета — `apps/api`, `apps/web`,
`packages/shared` — и между ними есть зависимость: `shared` должен собираться
раньше остальных. Плюс [ADR-009](./009-development-process.md) требует прогонять
lint, test, build и typecheck на каждый PR.

Нужно решить, оркеструем задачи скриптами pnpm или отдельным инструментом.

## Решение

Поверх pnpm workspaces используем **Turborepo**.

Пакеты объявляют скрипты из общего набора — `dev`, `build`, `lint`, `test`,
`typecheck` — а `turbo.json` в корне задаёт граф и кэширование. Корневые скрипты
(`pnpm build`, `pnpm lint`, ...) прокидываются в `turbo run`.

### Правила

- Скрипты, которых у пакета пока нет, объявлять не нужно: turbo молча пропускает
  такие пакеты
- Заглушки вида `echo "no tests" && exit 0` запрещены — дают в CI ложный зелёный
- `build` объявлен как `dependsOn: ["^build"]`: зависимости собираются первыми
- `dev` — `cache: false` и `persistent: true`
- Remote cache **не подключаем** на старте, только локальный

### Обоснование

- **Граф зависимостей.** `packages/shared` собирается до `apps/*` автоматически.
  Руками это цепочка `pnpm --filter` вызовов, которую забывают обновлять при
  добавлении пакета.
- **Кэш в CI.** Turbo пропускает пакеты, входы которых не менялись. При трёх
  пакетах это уже заметно, дальше только растёт.
- **Один `pnpm dev`** на весь monorepo вместо ручного `--parallel`.
- Стандартный инструмент экосистемы — команда учится на релевантном.

## Альтернативы

| Вариант                                | Почему отклонён                                                             |
| -------------------------------------- | --------------------------------------------------------------------------- |
| Чистый pnpm (`--filter`, `--parallel`) | Работает на двух пакетах, но граф сборки и кэш CI приходится держать руками |
| Nx                                     | Генераторы, плагины и граф Nx избыточны для трёх пакетов; выше порог входа  |
| Turborepo с remote cache сразу         | Нужен аккаунт и токены в CI; локального кэша хватает на старте              |

## Последствия

- В корне появляется `turbo.json`; новый пакет попадает в пайплайн ровно теми
  скриптами, которые объявил — забытый `lint` означает, что пакет молча не
  проверяется в CI
- CI стоит сохранять `.turbo/` между запусками, иначе кэш бесполезен
- Turbo кэширует по хэшу входов и объявленным `outputs`. Если задача пишет за
  пределы `outputs`, результат «не пересоберётся». Поэтому `outputs`
  объявляются явно, а при отладке кэша — `turbo run <task> --force`
