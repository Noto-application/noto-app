# ADR-017: S3-совместимое хранилище изображений

**Статус:** Accepted
**Дата:** 2026-10-30

## Контекст

Пользователям нужна загрузка аватара. Изображения следует хранить отдельно от
PostgreSQL, а метаданные объекта и связь с пользователем — в базе данных.
Текущий сценарий — только аватары. В дальнейшем общий storage слой можно будет
использовать для других целей, например изображений редактора, с отдельными
правилами авторизации и жизненного цикла. Их поддержку это решение сейчас не
внедряет.

Деплой приложения использует Docker Compose и Caddy. Загрузка напрямую из
браузера требует, чтобы подписанный URL был доступен браузеру, а не только
контейнеру API.

Локальный MinIO отклонён из-за лицензионных требований. Кроме того, официальные
community-образы больше не публикуются, а отдельный S3-стек (Docker,
Caddy-прокси, два endpoint’а) для учебного проекта избыточен. Yandex Object
Storage уже выбран для production и доступен команде.

## Решение

### Объектное хранилище

- Использовать S3 API через AWS SDK for JavaScript v3 и Yandex Object Storage
  (`https://storage.yandexcloud.net`, регион `ru-central1`) и в локальной
  разработке, и в production. Один приватный bucket на все среды.
- Локальный объектный сервер в Docker не запускается. Браузер и API обращаются
  к `https://storage.yandexcloud.net` напрямую. Caddy S3-трафик не проксирует
  и credentials хранилища не получает.
- Bucket всегда приватный. Публичный доступ к bucket и объектам отключён;
  доступ выдаётся только через короткоживущие presigned URL.
- Credentials (`AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`) доступны только
  API: локально в `apps/api/.env`, в production — в `runtime/api.env`. Значения
  в примерах — заглушки. Credentials не передаются браузеру или Caddy и не
  коммитятся в репозиторий.
- CORS bucket в консоли Yandex Cloud разрешает origin локального фронта
  (`http://localhost:8080`) и production-origin приложения, плюс методы и
  заголовки, нужные для presigned upload и чтения.
- Объекты адресуются непрозрачными случайными ключами, сформированными API.
  Имя файла, переданное клиентом, не используется как storage key.

Один bucket упрощает настройку: не нужно поднимать второе хранилище и
синхронизировать конфиги. Локальные и production-объекты лежат рядом; это
приемлемо, пока ключи непрозрачные, а объём — аватары учебной команды.

### Загрузка аватара

Загрузка выполняется напрямую из браузера в хранилище по presigned `PUT`, с
последующим подтверждением API:

1. Авторизованный клиент запрашивает у API разрешение на загрузку аватара.
   API проверяет применимые ограничения, создаёт запись объекта в состоянии
   `pending` и возвращает presigned URL, HTTP-метод и требуемые заголовки.
2. Клиент отправляет файл напрямую в Yandex Object Storage по подписанному URL.
3. Клиент вызывает API подтверждения загрузки. API проверяет наличие объекта
   и его фактические метаданные через хранилище; только после успешной проверки
   объект становится активным аватаром пользователя.
4. В одной транзакции PostgreSQL API активирует новый объект, обновляет ссылку
   пользователя и ставит прежний аватар в очередь отложенного удаления.
5. Ошибка загрузки или подтверждения не изменяет текущую ссылку на аватар.

Подтверждение должно быть идемпотентным для уже подтверждённой загрузки.
Неуспешная или просроченная загрузка оставляет текущий аватар без изменений;
неиспользованные pending-записи и соответствующие объекты подлежат очистке.

### PostgreSQL и модель данных

- PostgreSQL — источник истины для метаданных и связей; временные URL не
  сохраняются.
- Для загруженного объекта хранится как минимум внутренний ID, уникальный
  storage key, создавший его пользователь, тип содержимого, размер, статус
  жизненного цикла и время создания. В записи пользователя хранится
  nullable-ссылка на активный объект аватара (FK), а не URL.
- Ответ API для профиля может содержать временный URL чтения, сгенерированный
  для приватного объекта. Это URL-представление для клиента, а не значение,
  сохраняемое в PostgreSQL; при истечении клиент получает новое через API.
- API проверяет связь объекта с пользователем при подтверждении загрузки и
  разрешении чтения. Знание storage key или URL само по себе не предоставляет
  доступ.
- Общий storage слой не принимает произвольный bucket от вызывающего кода.
  Категория объекта и прикладной модуль определяют правила доступа. Изображения
  редактора смогут использовать тот же транспорт хранения, но их авторизация
  должна проверяться отдельно по ACL страницы/проекта; аватарные правила на них
  не распространяются. Сейчас реализуется только сценарий аватаров.

### Удаление и согласованность

PostgreSQL и S3 не поддерживают общую транзакцию. Поэтому текущий аватар
переключается в PostgreSQL только после подтверждения нового объекта. Старый
объект не удаляется синхронно: для него записывается `deleteAfter` (по
умолчанию через 24 часа), после чего фоновая задача удаляет объект и завершает
очистку записи.

Удаление выполняется идемпотентно и с повторными попытками. Ошибка удаления
не откатывает обновлённый профиль и не возвращает ссылку на старый аватар.
Записи pending и просроченные задачи удаления должны переживать перезапуск API,
поэтому их состояние хранится в PostgreSQL, а не только в памяти процесса.

### Docker и Caddy

- Корневой `docker-compose.yml` поднимает только Postgres и Redis. Объектное
  хранилище в Compose не входит.
- API получает параметры Yandex Object Storage через environment. Локальный и
  production-набор переменных совпадают: bucket, регион, endpoint, ключи доступа.
- Caddy проксирует `/api/*` к API и не проксирует S3. Presigned URL указывает
  на `https://storage.yandexcloud.net`.

## Последствия

- Ошибка загрузки не приводит к потере текущего аватара; удаление старого
  объекта можно повторять независимо от запроса обновления профиля.
- Прямой upload не нагружает API передачей бинарного тела, но требует настройки
  CORS на bucket и доступа в интернет из локальной разработки.
- PostgreSQL хранит ссылку на объект и его метаданные, но не бинарное содержимое
  и не временный URL.
- Очистка orphan/pending объектов требует фоновой задачи с устойчивым состоянием
  и идемпотентной обработкой ошибок.
- Локальные загрузки попадают в тот же bucket, что и production. Случайные
  storage key снижают риск коллизий имён; разделение бакетов можно ввести позже,
  не меняя контракт API.
- Будущие сценарии использования storage слоя, включая изображения редактора,
  потребуют собственной авторизации и не должны расширять права доступа к
  аватарам; сейчас эти сценарии не реализуются.

## Отклонённые альтернативы

| Вариант                                 | Почему нет                                                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Передавать файл через API               | Увеличивает сетевую нагрузку и память/ресурсы API; прямой presigned upload позволяет передавать файл в хранилище |
| Хранить бинарные данные в PostgreSQL    | Смешивает хранение метаданных с крупными объектами и усложняет масштабирование и обслуживание базы               |
| Хранить URL объекта в PostgreSQL        | Временный URL истекает и не является устойчивым идентификатором; в базе хранится storage key                     |
| Публичный bucket                        | Обходит авторизацию приложения и делает случайную выдачу URL постоянным публичным доступом                       |
| Удалять прежний аватар сразу при замене | Ошибка подтверждения или обновления профиля может привести к потере текущего изображения                         |
| Локальный MinIO в Docker                | Официальные образы недоступны; отдельный endpoint, Caddy-прокси и init-bucket не окупаются при уже выбранном Yandex Object Storage |
| Отдельный bucket на каждую среду        | Для текущего объёма (аватары, одна команда) дублирует CORS, ключи и документацию без выигрыша в контракте        |
