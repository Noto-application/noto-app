# ADR-002: Маршруты, домены и навигация

**Статус:** Accepted  
**Дата:** 2026-07-14

## Контекст

Приложение совмещает приватную рабочую зону (редактор, проекты) и публичный контент (SEO-статьи). Нужна понятная структура URL, совместимая с шарингом страниц и SEO.

## Решение

### Домены

| Домен           | Назначение                                | Когда                                               |
| --------------- | ----------------------------------------- | --------------------------------------------------- |
| `noto.app`      | Основное приложение + минимальный лендинг | Сейчас                                              |
| `blog.noto.app` | Публичные SEO-статьи                      | Позже (см. [RFC-004](../rfc/004-blog-subdomain.md)) |

### Маршруты на `noto.app`

| Путь                  | Зона    | Описание                              |
| --------------------- | ------- | ------------------------------------- |
| `/`                   | public  | Минимальный лендинг                   |
| `/login`, `/register` | public  | Страницы аутентификации               |
| `/app/*`              | private | Авторизованная зона                   |
| `/app/[pageId]`       | private | Текущая страница (основная навигация) |

После успешного логина пользователь перенаправляется в `/app`.

### Навигация — по аналогии с Notion

- **URL-first для страниц:** выбор Page в сайдбаре ведёт на `/app/[pageId]`. Выбор проекта и ссылки разделов следуют уточнению #172 ниже.
- **Проект не в URL Page:** на `/app/[pageId]` проект выводится из метаданных Page. На экранах без Page действует URL-контекст по уточнению #172.
- Работают deep links, «назад/вперёд» в браузере, шаринг ссылок на страницу

### Next.js route groups

```
apps/web/src/app/
├── (public)/           # лендинг, auth, позже — превью статей
│   ├── page.tsx        # /
│   ├── login/
│   └── register/
└── app/                # приватная зона
    ├── layout.tsx      # QueryClientProvider, auth guard
    └── [pageId]/
        └── page.tsx
```

### Публичные статьи (текущая фаза)

До выноса на `blog.noto.app` — в том же Next.js app, в route group `(public)`. Рендер через RSC (см. [ADR-004](./004-data-fetching.md)).

## Альтернативы

| Вариант                                    | Почему отклонён                   |
| ------------------------------------------ | --------------------------------- |
| `/app/projects/[projectId]/pages/[pageId]` | Длинные URL; Notion так не делает |
| Проект в URL, страница в Zustand           | Нет deep links на страницу        |
| `app.noto.app` для приложения              | Лишний поддомен на старте         |
| `/[slug]` на корне для статей              | Конфликт с маршрутами приложения  |

## Последствия

- Middleware защищает только `/app/*` (см. [ADR-003](./003-authentication.md))
- Сайдбар и дерево страниц синхронизируются с `[pageId]` из URL
- Миграция на `blog.noto.app` потребует отдельного RFC и не блокирует старт

## Уточнение #172: проект на экранах без Page

**Статус уточнения:** принято человеком 2026-11-08 вместе со спецификацией #172,
включая canonical `replace`, ограничения корневого создания и контекстную
ссылку «Домой». Уточняет область действия исходного Accepted-решения.

### Принято

Правило «Проект не в URL» относится к маршруту страницы `/app/[pageId]`: на нём
проект определяется метаданными Page, а `?projectId=` не является источником
истины и не может переопределить Page.

На экранах без открытой Page проектный контекст задаётся URL:

- `/app?projectId=<id>` — домашний экран проекта; переключатель в Sidebar ведёт
  сюда и не открывает произвольную Page;
- `/app/calendar?projectId=<id>` и `/app/trash?projectId=<id>` — проектные
  разделы; ссылки из Sidebar сохраняют текущий контекст;
- `/app/settings` — глобальный экран без проектного контекста.

`/app`, `/app/calendar`, `/app/trash` и `/app/settings` — зарезервированные
статические сегменты Next.js: они имеют приоритет над `/app/[pageId]` и не
являются Page. Реальные id Page — UUID по контракту `pagesContract`, поэтому
коллизия с зарезервированными словами не поддерживается.

- Отсутствие явного контекста не равно неверному контексту: fallback на первый
  доступный проект допустим только при отсутствии `projectId` и только на
  экранах, чей контракт это разрешает.
- Явный пустой, неоднозначный, невалидный или недоступный `projectId` даёт
  видимое состояние без silent fallback.
- Автосоздание «Мой проект» при пустом списке проектов — ограниченное
  исключение только по явному клику создания страницы после успешного пустого
  списка, без явного URL/Page-контекста; не на mount, при ошибке, в настройках
  или chooser корзины.

### Дополнительно принято (2026-11-08)

- Canonical `replace` на первый доступный проект, когда `/app` открыт без
  `projectId` (как уже делает календарь), только пока исходное навигационное намерение актуально.
- Корневое создание недоступно на `/app/settings` и chooser `/app/trash` без `projectId`.
- «Домой» сохраняет разрешённый контекст: `/app?projectId=<id>`; при настоящем отсутствии контекста — `/app`.
