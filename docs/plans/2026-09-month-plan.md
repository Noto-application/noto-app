## Как реализовывать основные части

### Календарь: сначала страницы, затем встречи

Общий фундамент — календарные записи внутри Project, со ссылкой на Page при необходимости. Предложение модели: CalendarEntry с projectId, nullable pageId, типом записи, датами для all-day либо start/end в UTC + IANA timezone для timed. Для календарной страницы заголовок берётся из Page, для самостоятельной встречи — собственный. Не хранить два редактируемых заголовка для одной страницы. Удалённые страницы и проекты исключаются; восстановление страницы возвращает её запись, если проект жив.

Этап A (в ядре): месяц, сегодня/предыдущий/следующий, клик по дню создаёт страницу с датой, клик по карточке открывает `/app/[pageId]`, смена даты формой и при наличии времени перетаскиванием. Это календарное представление страниц, не универсальные Notion databases с произвольными свойствами.

Этап B (дополнительно 16–24 ч): встречи без страницы, время начала/конца, неделя/день, часовой пояс; необязательная ссылка на страницу с заметками. Без повторений, приглашений по ICS и Google/Outlook sync.

Этап C (ещё 16–28 ч после B): одно TG-напоминание. Привязка аккаунта одноразовым токеном, BullMQ job, пересоздание/отмена при изменении события, проверка актуальности перед отправкой, повторные попытки без дублей. Не связывать базовый календарь с готовностью бота.

Предлагаемый REST-контракт: list по projectId и диапазону from/to, create, update, delete. Данные — TanStack Query; месяц, view и projectId — URL, например `/app/calendar?projectId=...&month=2026-09`; формы — RHF. API фильтрует по ACL и пересечению диапазонов. При ошибке переноса интерфейс возвращает предыдущую дату. All-day хранит календарную дату, а не «полночь UTC»; в спецификации явно определить исключительную правую границу диапазона.

Библиотека-кандидат: FullCalendar Standard. [Официальная React-интеграция](https://fullcalendar.io/docs/react) описывает React 17–19, кастомный JSX карточек и Next.js; [документация DnD](https://fullcalendar.io/docs/event-dragging-resizing) — перемещение/resize. [Standard под MIT; Premium имеет другие условия](https://fullcalendar.io/license). Для этого scope выбирать Standard. Альтернатива — [react-big-calendar](https://github.com/bigcalendar/react-big-calendar), MIT, с drag-and-drop addon. Первичный выбор — FullCalendar, окончательный после спайка 4–6 ч (включён в оценку календаря): Next.js build, тема, ru locale, touch, изменение даты, rollback. Версию фиксировать после спайка; примеры разных major не смешивать.

Библиотека покрывает UI, но не серверное хранение, ACL, часовые пояса бизнес-модели или доставку уведомлений.

### Проекты и участники

Использовать уже готовый Projects CRUD; отдельный Workspace не вводить, это соответствует ADR-011. Для пустого проекта нужен URL-контекст, например `/app?projectId=...`, иначе текущий хук создания вне страницы выбирает первый проект. После удаления выбранного проекта — переход в другой доступный или пустое состояние.

Предложение простого добавления: owner вводит email уже зарегистрированного пользователя → создаётся membership editor. В UI нет выбора роли, но существующие owner/editor/viewer и серверные проверки сохраняются. Это упрощённое добавление участника, не email-invite: приглашение незарегистрированного человека с письмом/токеном отдельно. Не дублировать участника; owner нельзя удалить/понизить; ограничить поиск по точному email. DTO возвращает текущую роль, чтобы frontend мог скрыть недоступные действия.

### Корзина

Нужно API списка и восстановления, soft-delete уже есть. Определить восстановление поддерева, удалённого родителя и ранее отдельно удалённых потомков. Предложение: идентификатор операции удаления, чтобы restore родителя не оживлял старый мусор; если родитель недоступен, восстанавливать выбранный корень в корень живого проекта. Восстановление и перемещение должны сохранять инварианты дерева. Проверять и Yjs-документ: удаление не должно приводить к повторному сохранению активной WS-сессией. Продуктовое решение по разрыву уже открытых соединений вынести в приёмку collab/корзины.

### Поиск и профиль

Поиск — серверный по заголовкам в доступных проектах, фильтр проекта, лимит/пагинация; удалённые не выдаются. Это полезный срез требования «поиск + фильтры» без индексации Yjs-контента.

Профиль в нижней части ядра — имя и его изменение; email пока read-only. Инициалы/цвет вычисляются стабильно. Загрузка аватара требует общего файлового слоя: не делать отдельную временную схему хранения только ради картинки.

## Dev-стенд и проверка готовности

Один сервер для первого стенда: reverse proxy с HTTPS → web, `/api` → api, WebSocket path → collab; Postgres/Redis во внутренней сети, постоянные volumes. API/collab secrets только серверные; проверить cookie/SameSite/origin на настоящем домене. Миграции — до переключения приложения. Образы тегируются коммитом; workflow для dev запускается после успешных проверок, с ограничением одновременных deploy. Откат образа отдельно от восстановления БД; несовместимые миграции требуют явного плана.

Базовая наблюдаемость в этом месяце: структурированные логи приложений, health/uptime, доступные метрики ресурсов и ошибок, понятное место просмотра, проверенное восстановление БД.
