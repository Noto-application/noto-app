# Spec: Yjs persistence — снапшоты в PostgreSQL

**Статус:** Draft
**Автор:** Stas Kobles
**Дата:** 2026-09-10
**Связанные:** [ADR-005](../../../../docs/adr/005-state-management.md), [ADR-006](../../../../docs/adr/006-realtime.md), [ADR-012](../../../../docs/adr/012-api-contract.md), RFC-003, issue #109; продолжает #108 (collab-auth) и разблокирует пользовательское включение #110

## Цель

Yjs-документ страницы переживает рестарт collab-сервера и повторное открытие:
состояние хранится в PostgreSQL. Без этого collab живёт только в памяти
Hocuspocus и теряется при перезапуске — из-за чего #110 нельзя включить
пользователям.

## Вне scope

- Миграция существующего REST-`content` страниц в Yjs (отдельная задача).
- История версий / ветвление документа (снимаем только актуальное состояние).
- Presence, комментарии, курсоры.
- ADR-013: realtime/CRDT-часть (store/load поверх живого Yjs) — спайк + ручная
  проверка (рестарт сервера), интеграционные автотесты **после** спайка.
  API-endpoint-ы (валидация, upsert, секрет, порядок версий) покрываем e2e
  сразу.
- Горизонтальное масштабирование collab (несколько инстансов на один документ)
  — вне scope: MVP = один инстанс (см. «Порядок записей»).

## Контракт

Persistence идёт **сервис-к-сервису**, по тому же паттерну изоляции, что #108:
collab-сервер (Hocuspocus) грузит/сохраняет состояние через **internal**
API-endpoint-ы, а DoStore/DoLoad Hocuspocus дебаунсит. БД трогает только
apps/api (единственный владелец Prisma).

Internal endpoint-ы (вне глобального `/api`, как `/internal/collab/authorize`;
защищены `X-Collab-Secret`; ts-rest-контракт в `@noto/shared/internal`):

- `GET /internal/collab/documents/:pageId`
  - `200 { state: string, version: number }` — base64 Yjs-update
    (`Y.encodeStateAsUpdate`) + сохранённая версия (collab продолжает счёт с неё).
  - `204` — снапшота ещё нет (новый документ, версию считаем `0`).
  - `403` — неверный секрет; `404` — страница удалена/не существует.
- `PUT /internal/collab/documents/:pageId`
  - body `{ state: string, version: number }` (base64 + монотонный номер), upsert.
  - `200` — сохранено; `400` — невалидный base64/Yjs-update; `409` — `version`
    не новее сохранённого (откат отклонён); `413` — превышен лимит размера;
    `403` — секрет; `404` — страница удалена.

`PUT` несёт монотонный `version` (см. «Порядок записей»); base64 обязан быть
валидным и декодироваться в непустой Yjs-update, иначе `400`, а размер сверх
лимита → `413` (см. «Крайние случаи»). Транспорт байтов — base64 в JSON
(бинарь — открытый вопрос).

Хранилище (Prisma):

```prisma
model PageCollabState {
  pageId    String   @id
  state     Bytes    // Y.encodeStateAsUpdate(doc) — полное состояние
  version   Int      @default(0) // монотонный номер записи (guard от отката)
  updatedAt DateTime @updatedAt
  page      Page     @relation(fields: [pageId], references: [id], onDelete: Cascade)
}
```

Признак режима — на самой странице (для #110, отдаётся фронту в DTO страницы):

```prisma
enum EditorMode { rest collab }
// в model Page:
editorMode EditorMode @default(rest)
```

## Поведение

1. Клиент подключается к `/collab` → #108 авторизует по cookie+членству и
   **решает режим страницы** (см. «Первый переход в collab»): уже `collab` →
   пускаем; ещё `rest` и страница пригодна (пустой REST-`content`) → промоутим
   в `collab` (персистентно) и пускаем; `rest` с непустым контентом →
   **отказ** (старую REST-страницу нельзя обнулить прямым WS).
2. **onLoadDocument** (collab): `GET …/documents/:pageId`. Есть снапшот →
   `Y.applyUpdate(doc, state)` и продолжаем счёт версий с загруженной; `204` →
   пустой документ, версия `0`. Ошибка/таймаут → **не** отдаём пустой док (это
   затёрло бы контент), а роняем загрузку — клиент видит «не synced» и повторяет.
3. Правки идут по Yjs между клиентами в реальном времени (#110).
4. **onStoreDocument** (дебаунс + max-интервал, и на отключении последнего
   клиента): кодируем **текущее** состояние `Y.encodeStateAsUpdate(doc)`,
   инкрементируем версию (от загруженной), `PUT …/documents/:pageId`. API
   атомарно пишет только если `version` больше сохранённого.
5. Рестарт collab-сервера → следующий onLoadDocument поднимает состояние **и
   версию** из PG; счёт продолжается, `409`-циклов после рестарта нет.

## Первый переход в collab (условие #110)

Режим страницы — durable `Page.editorMode`, но первый вход в collab не может
зависеть от уже выставленного `collab` (иначе новые `rest`-страницы туда не
попадут). Правило:

- **Фронт** открывает страницу в collab, если `page.editorMode === 'collab'`
  **или** (`NEXT_PUBLIC_COLLAB_ENABLED` поднят **и** страница пригодна — пустой
  `content`). Второе — путь первого входа (спайк-эвристика #110).
- **Сервер — источник истины**: на connect (#108) проверяет пригодность и
  промоутит `rest → collab` только для пустой страницы; страницу с REST-контентом
  в collab не пускает. Так прямое WS-подключение к старой странице не переключит
  её на пустой Yjs-документ.
- После промоута страница `collab` навсегда и открывается в collab независимо
  от флага.

**Гонка REST-PATCH ↔ промоут.** Другая вкладка могла держать REST-редактор и
отправить отложенный PATCH тела. Чтобы REST-контент не сохранился уже после
перехода (и не потерялся для Yjs), промоут и REST-запись тела **взаимно
исключающие и атомарные**:

- Промоут: `UPDATE Page SET editorMode='collab' WHERE id=? AND editorMode='rest'
  AND content = '[]'` (одним запросом). Затронул строку → промоут наш, пускаем.
  **0 строк → перечитать режим**: уже `collab` (промоутил другой одновременный
  клиент) → **пускаем** к общему документу; `rest` с непустым контентом →
  отказ. Проверки доступа/членства и удаления (#108) сохраняются.
- PATCH **тела** (`content`) разрешён только при `editorMode='rest'`: пишем
  условно (`... WHERE editorMode='rest'`), 0 строк → `409 CONFLICT` (страница
  перешла в collab; тело теперь живёт в Yjs). **Заголовок и прочие метаданные
  PATCH-аются как прежде**, независимо от режима.
- Итог гонки детерминирован: чья транзакция первой — та выигрывает; проигравший
  (переход или REST-запись тела) получает отказ. Ничего не сохраняется «мимо».

## Порядок записей и надёжность

**Порядок (P1-1).** MVP = **один** collab-инстанс. Дебаунс Hocuspocus сам по
себе **не** ждёт завершения предыдущей записи, поэтому сериализуем store
**сами**: на документ — цепочка промисов / мьютекс, одновременно не более одного
PUT, следующий ждёт предыдущий. Каждая запись кодирует **актуальное** состояние
в момент флаша (не отложенный старый payload); повтор после ошибки — тоже
текущее состояние.

Версия — монотонный счётчик на документ, **инициализируется из GET при загрузке**
(после рестарта/повторного открытия продолжаем с сохранённой, а не с нуля).

Guard на API — **атомарный**: условная запись одним запросом
(`UPDATE … SET state, version WHERE version < :version`, плюс вставка если
строки нет), не read-then-write. Иначе два PUT могли бы оба пройти проверку и
записаться в обратном порядке. При проигрыше гонки/устаревшей версии → `409`,
прежнее состояние сохраняется.

Несколько инстансов на один документ — вне scope (потребует внешней координации).

**Частота store (P1-3).** Два параметра:
- `debounce` (~2s) — записать после паузы в правках;
- **`maxWait`** (~10s) — принудительный store даже при **непрерывном** вводе,
  иначе debounce откладывал бы запись бесконечно и окно потери росло.

**Гарантия потери** (только при исправной БД): не больше `maxWait` + время
записи. При недоступной БД гарантия **не действует** — окно растёт до
восстановления (retry ниже); это осознанное ограничение.

**Сбой сохранения и shutdown (P1-2).**
- Ошибка/недоступность API/БД на store → **retry с backoff**, каждый повтор
  кодирует текущее состояние (не копит очередь старых payload-ов). Новых правок
  для повтора не требуется; после восстановления БД сохраняется без ввода.
- **Штатный shutdown** (SIGTERM): flush всех открытых документов, дождаться — но
  с **пределом ожидания** (напр. 5s): если БД недоступна, не висим вечно, а
  выходим, зафиксировав потерю (правки этой сессии не сохранены).
- **Отключение последнего клиента** документа → финальный store.
- **Аварийный краш** (SIGKILL) → теряются правки с последнего успешного store;
  окно ограничено `maxWait` + время записи (при исправной БД). Допустимое MVP.

## Крайние случаи

- **Ошибка load** → загрузка документа проваливается (не пустой док), чтобы не
  затереть сохранённое. Fail-closed по данным.
- **Страница удалена** (soft-delete) во время сессии → store получает `404`,
  снапшот не пишем; существующий снапшот удаляется каскадом при hard-delete
  страницы (`onDelete: Cascade`).
- **Конкурентные / запоздавшие store** → guard по `version`: запись со
  `version <=` сохранённого отвергается (`409`), предыдущее состояние
  сохраняется. Не даём старому payload-у откатить новый.
- **Невалидный payload** (не base64 / не декодируется в Yjs-update / пустой) →
  `400`, строку в БД **не трогаем** (upsert только валидного).
- **Превышение лимита** размера снапшота (конфигурируемый предел, напр. 8 MB) →
  `413`, существующее состояние сохраняется. Лимит тела запроса выставить в
  Fastify/Nest.
- **Неверный/пустой секрет** → `403`, как в #108.
- **Гонка REST-PATCH тела ↔ промоут в collab** → e2e на оба исхода: REST-запись
  успела первой → промоут отклонён (страница остаётся `rest` с контентом);
  промоут первым → PATCH тела получает `409`, заголовок PATCH-ается.
- **Два одновременных первых подключения** к пустой странице → оба успешны,
  промоут `rest→collab` выполнен ровно один раз (проигравший UPDATE перечитал
  режим и пустил к общему документу).

## Взаимодействия

- **Источник истины** для collab-страниц — Yjs-снапшот, не REST-`content`.
  REST-`content` в collab-режиме не пишется (#110), миграция вне scope.
- **#110 rollout**: durable признак режима — колонка `Page.editorMode`
  (не наличие снапшота: страница уже в collab до первого store). Ставится в
  `collab` при первом подключении к странице (шаг 1 «Поведение»), отдаётся
  фронту в **DTO страницы** (`GET /pages/:id` → добавить `editorMode`).
  `PageEditor` выбирает режим по правилу из «Первый переход в collab»
  (`editorMode==='collab'` **или** флаг+пустая страница), не только по полю.
  Обновить ts-rest контракт страницы в `@noto/shared` (+ фронт #110 переключить).
- **Изоляция** — те же правила, что #108: `/internal/*` не роутится Caddy,
  секрет обязателен, endpoint не в обход Caddy (деплой).
- **Prisma/миграция** — новая модель + миграция в apps/api.

## Открытые вопросы

- Тюнинг `debounce`/`maxWait`/shutdown-timeout (черновик 2s/10s/5s).
- Транспорт: base64-в-JSON или бинарный body (`application/octet-stream`)?
- Нужна ли проверка членства на load/store, или достаточно сервисного секрета
  (хендшейк #108 уже авторизовал сессию)? Предлагаю: только секрет.
- Растёт ли снапшот без границ (Yjs tombstones) — нужен ли периодический
  `gc`/re-encode; вероятно вне scope #109.
- Точный лимит размера снапшота (8 MB — черновой).
