## Цель

Дать проекту представление «страницы по дням»: календарная запись связывает
Page с календарной датой (date-only). Пользователь планирует страницу на день,
переносит дату и снимает её, не меняя базовую модель Page.

## Вне scope

- Timed-события, время, IANA timezone, week/day view — не обещаем и не
  закладываем «на будущее» в форму.
- Восстановление из корзины и восстановление проекта — внешняя зависимость
  (#128), см. «Жизненный цикл».
- Самостоятельные записи без Page (Notion databases, произвольные свойства),
  recurrence, ICS, внешний sync, Telegram-напоминания.
- Realtime-синхронизация календаря и обязательный DnD.
- UI, URL и блок редактора — во
  [frontend spec](../../../../apps/web/src/entities/calendar-entry/calendar.spec.md).

## Контракт

ts-rest контракт в `@noto/shared`, Zod-схемы — источник типов и runtime
([ADR-012](../../../../docs/adr/012-api-contract.md)); ошибки — общий shape
`{ code, message, details? }`. Доменный контракт не зависит от выбранной
библиотеки календаря: FullCalendar — лишь кандидат
([RFC-005](../../../../docs/rfc/005-supplementary-libraries.md) — Draft, не
утверждён; финальный выбор — #133).

### Модель

`CalendarEntry` — **отдельная опциональная 1:1 запись к Page**. Минимум:
`pageId` (уникальный/идентифицирующий FK), `date` (date-only), `updatedAt`.
`projectId` и `title` в записи **не хранятся** — выводятся из Page.
Заголовок всегда `Page.title`.

| Поле        | Тип          | Заметка                                           |
| ----------- | ------------ | ------------------------------------------------- |
| `pageId`    | `uuid`       | уникальный, идентифицирует запись                 |
| `date`      | `YYYY-MM-DD` | календарная дата, date-only, без времени и зоны   |
| `projectId` | `uuid`       | только в ответе, выводится из Page                |
| `title`     | `string`     | только в ответе, `Page.title`                     |
| `updatedAt` | ISO          | хранимая метадата записи, обновляется при мутации |

**Принятое решение — CalendarEntry, не nullable `Page.date`.**
`Page.date` проще и атомарна, но смешивает календарный жизненный цикл с
базовым Page DTO и pages autosave. Отдельная запись локализует календарный
контракт и сохраняется при soft-delete Page. Альтернатива `Page.date`
отклонена (бывший открытый вопрос №1, см. «Решения»).

### Эндпоинты

| Метод | Путь                                                                  | Кто       | Успех                                                                      |
| ----- | --------------------------------------------------------------------- | --------- | -------------------------------------------------------------------------- |
| GET   | `/projects/:projectId/calendar-entries?from=YYYY-MM-DD&to=YYYY-MM-DD` | `viewer`+ | `200 { entries[] }`                                                        |
| GET   | `/projects/:projectId/calendar-entries/:pageId`                       | `viewer`+ | `200 { entry: CalendarEntry \| null }` (расширение #136)                   |
| POST  | `/projects/:projectId/calendar-pages`                                 | `editor`+ | `201 { page, entry }`; replay `200 { page, entry: CalendarEntry \| null }` |
| PUT   | `/projects/:projectId/calendar-entries/:pageId`                       | `editor`+ | `200 { entry: CalendarEntry \| null }`                                     |

Коды ошибок: `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404,
`VALIDATION_ERROR` 400, `CONFLICT` 409 — существующий `apiErrorCodeSchema`,
новый код не вводим. `409 CONFLICT` несёт две независимые семантики:
несовпадение payload по ключу идемпотентности create и CAS mismatch PUT
(см. «Поведение»); они не смешиваются.

### ACL

Enforcement — на сервере всегда, по
[ADR-011](../../../../docs/adr/011-authorization-acl.md) (`ProjectAccessGuard` +
`@RequireProjectRole`). Несуществующий/удалённый проект или страница →
`404 NOT_FOUND`. Активный участник без достаточной роли или без членства →
`403 FORBIDDEN` с обезличенным телом без приватных данных. Принято оставить
конвенцию ADR-011 без изменений: несуществующее/удалённое → `404`, отсутствие
членства/недостаточная роль → `403`; глобальная нормализация не-раскрытия
существования для посторонних в рамках календаря не вводится (бывший открытый
вопрос №2, см. «Решения»).
Replay create и PUT перепроверяют ACL на каждом вызове так же, как свежий
запрос, и не кэшируют результат исходного вызова.
Точечный GET использует тот же порядок `ProjectAccessGuard`: после
аутентификации проверяется существование/активность проекта (`404`), затем
членство и роль (`403`), затем ts-rest валидирует path params и проверяется
доступность Page в этом проекте (`404`). Guard выполняется до path validation:
невалидный `projectId` при поиске проекта даёт `404`, а не `400`; невалидный
`pageId` даёт `400` только после успешной аутентификации и доступа `viewer`+
к активному проекту. Этот существующий порядок не меняется для нового GET.
Отказ не раскрывает скрытую Page или приватные данные/роли участников.
Новые роли, capabilities и изменения остальных guards не требуются.

### Инварианты

- В первом релизе максимум одна `CalendarEntry` на Page (1:1) — одна
  календарная дата. Это не диапазон: нет `start`/`end`, времени суток и
  timezone.
- `projectId` и `title` не хранятся в записи — выводятся из Page.
- `date` — date-only (`YYYY-MM-DD`), без времени и IANA timezone.
- Иерархия Page не влияет на календарные даты: родительская и каждая дочерняя
  Page планируются независимо. Дата родителя не наследуется потомками;
  изменение или снятие даты родителя не меняет даты поддерева;
  назначение/изменение даты дочерней Page не затрагивает родителя и siblings.
  Перемещение Page в дереве не меняет её календарную дату.
- create атомарен: Page и запись создаются вместе; ключ идемпотентности —
  пара `(projectId, clientRequestId)`; дублей Page/записей при повторе и при
  конкурентных одинаковых create нет (ровно один `201`, остальные — `200`);
  replay ничего не создаёт и не восстанавливает и перепроверяет ACL.
- PUT — desired-state CAS: сначала «текущая дата == `date`» → `200` no-op
  (устаревший `expectedDate` не мешает), затем «текущая дата == `expectedDate`»
  → применить, иначе `409`. Снятие даты удаляет только запись и сохраняет Page.
  Для конкурентных PUT с общим `expectedDate = E` и начальной датой `C`: при
  `E == C` с разными целями, обе `≠ C`, — ровно один `200` и один `409`, с
  одинаковыми целями — оба `200`; если одна цель `== C`, результат зависит от
  порядка (`[200, 200]` или `[200, 409]`), итог — ненулевая цель; при `E != C`
  цель `== C` — `200` no-op, цель `≠ C` — `409`.
- ACL всегда серверный: несуществующее/удалённое → `404`, недостаток роли/
  членства → `403` без приватных данных.
- list фильтрует удалённые Page/поддеревья/проект и укладывается в
  `[from, to)`, `from < to`, максимум 42 дня. Изоляция строго по `projectId`
  пути: даже если вызывающий — участник нескольких проектов, возвращаются
  только записи запрошенного проекта.

## Поведение

### list

`GET .../calendar-entries?from&to` — записи проекта в полуинтервале
`[from, to)`. `from`/`to` — строгие календарные даты (`YYYY-MM-DD`, без
времени и зоны), `from < to`, максимум **42 календарных дня** в диапазоне;
иначе `400 VALIDATION_ERROR`. Ответ — `{ entries }`, каждый элемент содержит
`pageId`, `projectId`, `title` (из Page), `date`, `updatedAt`. Выдача
фильтрует удалённые Page, любую Page под soft-deleted поддеревом (текущий
delete помечает всё поддерево) и удалённый Project. Изоляция — строго по
`projectId` из пути: записи других проектов не попадают в ответ, даже если
вызывающий состоит в них.

### Точечное чтение (расширение #136)

`GET .../calendar-entries/:pageId` возвращает `{ entry }` для одной текущей
Page независимо от месяца и открытых диапазонов календаря. Используются
существующие `calendarEntryResponseSchema` и path params `calendarEntryParamSchema`
из shared-контракта; `projectId` и `pageId` — UUID. Наблюдаемые статусы учитывают
порядок guard до ts-rest validation: без авторизации — `401`, невалидный
`projectId` — `404 NOT_FOUND` при поиске проекта; невалидный `pageId` —
`400 VALIDATION_ERROR` только после доступа `viewer`+ к активному проекту.
Отказ guard (`401`/`404`/`403`) имеет приоритет перед валидацией `pageId`.
Успешное чтение доступно `viewer`/`editor`/`owner`.

- `200 { entry: null }` означает: активная доступная Page проверена, записи нет.
  Это не обозначение неизвестного состояния или отсутствующей Page.
- Запись есть → `200 { entry: CalendarEntry }`, даже если дата вне видимого
  месяца. `title`/`projectId` по-прежнему выводятся из Page.
- Page отсутствует, удалена или принадлежит другому проекту → `404 NOT_FOUND`,
  не `200 null`; удалённый/отсутствующий проект также даёт `404`.
- Page под удалённым предком недоступна (`404`): используется существующий
  каскадный soft-delete поддерева и serializable-инвариант Pages, а не новая
  архитектура рекурсивных проверок предков. Проверка этого случая в тестах —
  через существующее каскадное удаление предка.
- Без аутентификации → `401`; постороннему в активном проекте → `403` по
  существующему порядку guard, без выдачи записи или приватных данных.

Это только чтение: probing-мутации, сканирование всех диапазонов и новое поле
в Page DTO не вводятся. Лимит list в 42 дня не меняется; миграция не нужна.

### create

`POST .../calendar-pages`, тело: `title` (правила Page: 1..200, trim),
`date`, `clientRequestId` (UUID). Первый вызов атомарно создаёт Page **в корне
проекта** (`parentId = null`, в конец корневых siblings) и `CalendarEntry` на
`date`, отвечает `201 { page, entry }`.

Ключ идемпотентности — **по проекту**: уникальна пара
`(projectId, clientRequestId)`. `projectId` задаёт пространство имён и **не
дублируется** в сравниваемом payload. Тот же `clientRequestId` в другом проекте
— независимый свежий create (`201`), а не replay. Тот же ключ в том же проекте —
replay исходного create, в том числе когда его прислал другой участник с
достаточной ролью: сначала прогоняются текущие ACL/доступность вызывающего,
затем сверка payload.

Сравниваемый payload (fingerprint) — нормализованные `{ title, date }`:
`title` после trim/валидации, `date` в каноническом `YYYY-MM-DD`. Сырые байты
запроса не сравниваются; `title`, отличающийся только краевыми пробелами, —
тот же payload. Изменение `title` или `date` относительно fingerprint →
`409 CONFLICT`. Fingerprint — нормализованный payload **исходного** create;
последующее переименование Page или снятие даты на него не влияют.

Повтор с тем же `clientRequestId` — это replay исходного create, а не команда
восстановить/сбросить Page или запись. Replay **ничего не создаёт и не
восстанавливает**: он заново прогоняет текущие ACL/access-проверки и
возвращает **текущее** состояние ресурса. Порядок проверок: сначала ACL/
доступность, затем сверка payload.

- Нет членства или недостаточная роль → `403 FORBIDDEN` (как у свежего
  запроса).
- Проект или созданная ранее Page отсутствует/удалён(а) → `404 NOT_FOUND`,
  без возврата и без восстановления.
- Входной payload сравнивается с нормализованным fingerprint исходного запроса
  (а **не** с текущими `title`/`date` Page и не с сырыми байтами). Тот же ключ в
  том же проекте с другим исходным payload → `409 CONFLICT` — это **только**
  несовпадение payload по ключу идемпотентности, семантически отдельно от PUT
  CAS `409`.
- Валидный replay (ACL пройден, payload совпадает) → `200 { page, entry }`:
  текущая Page и текущая запись; если дата снята и записи больше нет —
  `entry: null`.

### update (PUT, desired-state CAS)

`PUT .../calendar-entries/:pageId`, тело
`{ date: YYYY-MM-DD \| null, expectedDate: YYYY-MM-DD \| null }`.

Правила проверяются по порядку, первое подходящее выигрывает:

1. текущая дата == `date` → идемпотентный успех `200`, тот же результат;
   `expectedDate` **не проверяется** (в том числе устаревший);
2. иначе текущая дата == `expectedDate` → назначить / изменить / снять дату
   (`200`);
3. иначе → `409 CONFLICT` (CAS mismatch).

Проверка и применение наблюдаемо атомарны и линеаризуемы. Для двух
конкурентных PUT с общим `expectedDate = E` и начальной датой `C` (до обоих
запросов):

- `E == C` и одинаковые целевые даты → оба `200`;
- `E == C` и разные целевые даты, обе `≠ C` → ровно один `200` и один `409`;
- `E == C` и одна целевая дата `== C` → допустимы как `[200, 200]`, так и
  `[200, 409]` в зависимости от порядка; итоговое состояние — ненулевая
  (не-no-op) цель;
- `E != C` и целевая дата `== C` → `200` no-op; `E != C` и целевая дата `≠ C`
  → `409` (для каждого запроса).

Внутренняя реализация атомарности (транзакция, уникальный индекс, блокировка)
не предписывается.

`409` PUT — это CAS mismatch и семантически **отдельно** от `409` create
replay (несовпадение payload по ключу идемпотентности).

`date = null` снимает **только запись**, Page сохраняется; ответ
`{ entry: null }`. Назначение существующей Page (включая вложенную) — та же
операция: Page без записи имеет текущую дату `null`, значит
`expectedDate: null` и `date` дня. Операция сохраняет её `parentId` и
структуру дерева. Сервер проверяет, что Page принадлежит проекту из пути:
чужая, отсутствующая или удалённая Page → безопасный `NOT_FOUND`;
**перепривязка Page в другой проект невозможна**. Ответ несёт достаточно
метаданных Page/записи для обновления кэша, но не описывает внутренности
реализации.

## Жизненный цикл

- Запись остаётся при soft-delete Page; существующее будущее восстановление
  Page снова делает её видимой, если проект активен и доступен. Отдельного
  «восстановления календаря» нет.
- Восстановление Project — вне scope.
- **Внешняя зависимость:** #128 — OPEN, frontend-only; в его теле признано
  отсутствие не созданной backend-задачи list/restore. Сквозная приёмка
  restore не может пройти, пока этот backend-контракт/issue не появится;
  написание спеки и остальное поведение календаря не заблокированы.

| Два PUT при `E == C`, разные target (оба `≠ C`)                                 | Один `200`, второй `409` (CAS)                                           |
| Два PUT при `E == C`, одинаковые target                                         | Оба `200`, без дубля                                                     |
| Два PUT при `E == C`, одна target `== C`                                        | `[200, 200]` или `[200, 409]` по порядку; итог — ненулевая цель          |
| Page под удалённым поддеревом или проектом                                      | Не попадает в list                                                       |

## Взаимодействия

- `@noto/shared` — ts-rest-контракт и Zod-схемы
  ([ADR-012](../../../../docs/adr/012-api-contract.md)); существующий тип
  `Page` переиспользуется, локальный урезанный DTO не вводится.
- `@noto/api` — контроллер + `ProjectAccessGuard`/`@RequireProjectRole`
  ([ADR-011](../../../../docs/adr/011-authorization-acl.md)).
- Frontend потребляет через TanStack Query; URL, состояние, блок редактора —
  во [frontend spec](../../../../apps/web/src/entities/calendar-entry/calendar.spec.md).
- Restore — #128 (внешняя зависимость, см. «Жизненный цикл»).

## Решения

Ниже — принятые решения спеки. Ранее открытые вопросы подтверждены и
перенесены сюда.

- Модель — отдельная `CalendarEntry` 1:1 к Page (см. «Модель»), принято;
  альтернатива nullable `Page.date` отклонена.
- Конвенция ADR-011 сохраняется: несуществующее/удалённое → `404`,
  членство/недостаточная роль → `403`; глобальная нормализация не-раскрытия не
  вводится.
- Лимит диапазона — 42 календарных дня, принят как предохранитель под месячную
  сетку (6 недель); пересматривается при недельном/ином представлении.
- Назначение существующей Page — в v1: небольшое расширение той же формы и
  API, нужно для практического снятия/возврата, новый тип данных не вводится.
- Снятие даты удаляет только запись; Page живёт дальше.
- PUT — desired-state CAS: сначала «текущая дата == `date`» → no-op `200`
  (устаревший `expectedDate` не проверяется), затем «текущая дата ==
  `expectedDate`» → применить, иначе `409`. `409` PUT — CAS mismatch,
  семантически отдельно от create replay.
- Ключ идемпотентности create — пара `(projectId, clientRequestId)`; в
  fingerprint входит только нормализованный `{ title, date }` исходного
  запроса. Replay перепроверяет ACL (`403`/`404`), ничего не создаёт и не
  восстанавливает и возвращает текущее состояние; `409` create — только
  несовпадение нормализованного payload с исходным.
- list изолирован по `projectId` пути: записи других проектов не смешиваются,
  даже если вызывающий состоит в них.
- `projectId` и `title` не дублируются в записи — выводятся из Page.
- Создание из календаря — всегда корневая Page (`parentId = null`).
- Для #136 человек согласовал 2026-10-31 точечный GET `viewer`+ с проверенным
  nullable-ответом и существующим ACL; мутационные контракты не меняются.
  Расширение реализовано; SPEC/TEST-gates и независимый CODE-review пройдены.

## Критерии приёмки

- На Page не более одной календарной записи — одной date-only даты, не
  диапазона.
- `title` и `projectId` в ответах всегда соответствуют Page и не хранятся в
  записи.
- Дата — date-only: в разных timezone она не сдвигается.
- Даты не зависят от иерархии: дата родителя не наследуется и её
  изменение/снятие не меняет поддерево; назначение/изменение даты дочерней
  Page не затрагивает родителя и siblings; перемещение Page не меняет её дату.
- create атомарен и скоупит ключ идемпотентности по проекту
  `(projectId, clientRequestId)`; сравнивает нормализованный `{ title, date }`
  исходного запроса (не сырые байты и не текущие значения Page); конкурентные
  одинаковые create дают ровно одну Page и одну запись; replay перепроверяет
  ACL (`403`/`404`), ничего не создаёт и не восстанавливает, возвращает
  текущее состояние (`entry: null`, если дата снята); `409` create — только
  несовпадение нормализованного payload с исходным.
- PUT — desired-state CAS в порядке «текущая == `date`» → no-op `200`,
  «текущая == `expectedDate`» → применить, иначе `409`; при `E == C` с разными
  целями, обе `≠ C`, — ровно один `200` и один `409`, с одинаковыми целями —
  оба `200`, а при одной цели `== C` результат зависит от порядка (`[200, 200]`
  или `[200, 409]`), итог — ненулевая цель; при `E != C` цель `== C` — no-op,
  цель `≠ C` — `409`. Снятие даты сохраняет Page; `409` PUT отделён от create
  replay.
- ACL/жизненный цикл: `403`/`404` по ADR-011, удалённые Page/поддеревья/
  проекты не попадают в list; list изолирован по `projectId` пути — участник
  нескольких проектов видит только записи запрошенного.
- list ограничен полуинтервалом `[from, to)`, `from < to`, максимум 42 дня.
- #136, контрактные/API-тесты точечного GET: `200 entry` (в том числе
  вне месяца), `200 null` только для активной доступной Page без записи;
  `401` без авторизации; невалидный `projectId` → `404`, невалидный `pageId` →
  `400` только после доступа `viewer`+ к активному проекту (до этого приоритет
  у `401`/project `404`/project `403`); `403` постороннему, чтение для всех
  трёх ролей, `404` для чужой/отсутствующей/удалённой Page и проекта,
  а также потомка после каскадного удаления предка. Проверяются общий shape
  ошибок, отсутствие приватных данных и сохранение порядка project guard.
