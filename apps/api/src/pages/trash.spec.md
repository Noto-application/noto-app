# Spec: Корзина страниц — список и восстановление одной страницы

**Статус:** Ready
**Дата:** 2026-10-05
**Связанные:** [ADR-011](../../../../docs/adr/011-authorization-acl.md), [ADR-012](../../../../docs/adr/012-api-contract.md), [ADR-013](../../../../docs/adr/013-spec-driven-development.md), [pages.spec.md](./pages.spec.md), [calendar.spec.md](../calendar/calendar.spec.md), issue #156

## Цель

Дать пользователю корзину проекта: плоский список удалённых страниц и
восстановление **одной** страницы. Восстановление возвращает страницу в дерево
проекта, сохраняя её содержимое; поддерево и предки автоматически не
восстанавливаются.

## Вне scope

- Восстановление проекта — отдельная задача (в `projects.spec.md`).
- Поддеревом/пакетом: восстановление детей, предков, «восстановить всё» —
  не делаем.
- Хранилище корзины как фича: TTL, автоочистка, purge/физическое удаление —
  отдельно.
- Перепривязка (reparent) при восстановлении — не делаем.
- UI, URL, frontend-состояние — отдельно.
- Миграция схемы и заполнение/починка исторических строк — не требуется и не
  делается (см. «Решения»).

## Контракт

ts-rest-контракт в `@noto/shared`, Zod-схемы — источник типов и runtime
([ADR-012](../../../../docs/adr/012-api-contract.md)); ошибки — общий shape
`{ code, message, details? }`.

| Метод | Путь                                            | Кто       | Успех                         |
| ----- | ----------------------------------------------- | --------- | ----------------------------- |
| GET   | `/projects/:projectId/trash/pages?limit&cursor` | `viewer`+ | `200 { pages[], nextCursor }` |
| POST  | `/pages/:pageId/restore`                        | `editor`+ | `200 { page }`                |

Коды ошибок: `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404,
`CONFLICT` 409, `VALIDATION_ERROR` 400 — существующий `apiErrorCodeSchema`,
новый код не вводим.

**Форма элемента корзины** (`TrashPage`, отдельная схема, не публичный `Page`):

| Поле        | Тип              | Заметка                                   |
| ----------- | ---------------- | ----------------------------------------- |
| `id`        | `string` (uuid)  |                                           |
| `projectId` | `string` (uuid)  |                                           |
| `parentId`  | `string \| null` | Родитель в дереве до удаления             |
| `title`     | `string`         |                                           |
| `position`  | `number` (int)   | Позиция на момент удаления                |
| `deletedAt` | `string` (ISO)   | Всегда не `null` — элемент по определению |

`content` в элемент списка **не входит**. Публичный `Page`
(`schemas/page.ts`) не переиспользуется, потому что всегда несёт `content`.

**Ответ списка:** `{ pages: TrashPage[], nextCursor: string | null }`;
`nextCursor: null` — страниц больше нет.

**Ответ restore:** `{ page }` — обычный `Page` DTO (с `content`).

## Поведение

### list (корзина)

- `viewer`+, проект из пути (`ProjectAccessGuard`): несуществующий или
  удалённый проект → `404`.
- Все страницы проекта с `deletedAt != null`, **плоско, на любой глубине**,
  включая потомков удалённых предков. Поддеревья не сворачиваются, корень
  корзины отдельно не выделяется.
- Изоляция строго по `projectId` из пути: страницы других проектов не
  попадают в ответ, даже если вызывающий состоит в них.
- Поля — строго `TrashPage`; `content` не отдаётся.
- Порядок детерминирован: `deletedAt DESC, id ASC`. `id` — тайбрейкер, потому
  что `deletedAt` не обязан быть уникальным.
- Пагинация — keyset по паре `(deletedAt, id)`: `limit` по умолчанию **50**,
  максимум **100**; `cursor` непрозрачный (клиент не разбирает и не собирает
  его сам, а возвращает эхо). `nextCursor` выдаётся, когда есть ещё строки.
  Невалидный/битый `cursor` или `limit` вне `1..100` → `400 VALIDATION_ERROR`.
- **Пагинация не является снапшотом.** Между страницами список может меняться
  (новые удаления, восстановления); read-your-writes по страницам и
  транзакционная консистентность не гарантируются. Гарантия — только
  детерминированный порядок и стабильный keyset-cursor. Это не курсор по
  историческому снимку.
- `cursor` из другого проекта данные не раскрывает: позиция применяется в
  рамках запрошенного `projectId`.

### restore (одна страница)

- `editor`+, item-роут `/pages/:pageId/restore` (как остальные item-роуты,
  [pages.spec.md](./pages.spec.md)).
- Доступ **deleted-aware**: `projectId` резолвится из страницы (она может быть
  удалена), проект должен быть живым. Порядок — существование (404) раньше прав
  (403), как в [ADR-011](../../../../docs/adr/011-authorization-acl.md).
  `PageAccessGuard` для restore не переиспользуется и не ослабляется: это
  отдельная резолюция, применимая только к этому роуту; остальные item-роуты
  сохраняют текущую семантику.
- Предусловия в порядке проверки:
  1. страница существует и `deletedAt != null`, проект жив → иначе `404`;
  2. членство и роль `editor`+ → иначе `403` (обезличенное тело);
  3. дерево пригодно для возврата → иначе `409 CONFLICT`: вся цепочка предков
     (`parentId != null`) жива **и** актуальная глубина восстанавливаемой
     страницы с учётом всех живых предков ≤ **10** (лимит дерева,
     [pages.spec.md](./pages.spec.md) «Вложенность»). Предка могли переместить,
     пока страница лежала в корзине, поэтому одной проверки «предок жив»
     недостаточно: глубина считается по текущему дереву, а не на момент
     удаления.
- Эффект: `deletedAt = null`. Сохраняются `id`, `projectId`, `parentId`,
  `title`, `content`, `editorMode`, Yjs-снапшот (`PageCollabState`) и
  `CalendarEntry`. Позиция **не восстанавливается**: страница добавляется в
  конец (append) группы живых сиблингов исходного `parentId`; при
  `parentId = null` — в конец корневых.
- Дети остаются удалёнными. Предки не восстанавливаются. Автоматического или
  пакетного восстановления нет, никаких выводов «за компанию».
- Повтор: цель уже живая → `404` (restore применим только к удалённой странице;
  живая в корзине отсутствует).

## Инварианты

- **I1 (active child ⇒ active parent).** Живого ребёнка под удалённым или
  отсутствующим родителем быть не может. Гарантия — **операционная**: для
  состояния, валидного по I1, операции delete/move/restore/create в
  serializable-протоколе сохраняют I1 (индуктивный шаг). Исторические строки,
  уже нарушившие I1 из-за прежней гонки create/delete, остаются как есть;
  задача их не чинит и I1 на них не распространяет — см. «Решения»,
  «Открытые вопросы».
- **I2 (no reparent).** Restore не меняет `projectId` и `parentId`.
- **I3 (календарь).** Restore не создаёт и не удаляет `CalendarEntry`; запись
  переживает soft-delete и снова становится видимой — согласовано с
  [calendar.spec.md](../calendar/calendar.spec.md) («Жизненный цикл»).
- **I4 (граница проекта).** Restore и list ограничены проектом страницы;
  список не смешивает проекты.

### Гонки и граница согласованности

- **delete** (каскад поддерева) и **move** уже выполняются в serializable-
  транзакции (`pages.service.ts`). **restore** должен идти в том же протоколе:
  проверка предков и снятие `deletedAt` — в одной serializable-транзакции,
  иначе restore, конкурирующий с delete/move родителя, может вернуть живого
  ребёнка под удалённым родителем (нарушение I1).
- **create — обязательная часть #156.** Сейчас `resolveParentId` вызывается
  **вне** транзакции на обоих путях (append и явной позиции), поэтому
  конкурентный delete может собрать поддерево до вставки нового ребёнка, и
  create вставит живого ребёнка под уже удалённым родителем. Чтобы I1 держался,
  create обязан проверять родителя/глубину **внутри** той же serializable-
  транзакции, что и запись, **на обоих путях**. Выбор «в #156 или отдельной
  задачей» не оставляем: без этого исправления I1 не держится и #156 не
  закрывается, поэтому правка create входит в объём #156.
- **Отзыв членства (revocation).** Между guard и коммитом роль могла быть
  отозвана. В restore-транзакции членство/роль перечитываются, решение
  принимается по снапшоту транзакции, а не по wall-clock-времени коммитов:
  - Если restore **стартует после коммита отзыва** (снапшот уже включает отзыв)
    — `403`, страница остаётся удалённой. Это обязательный детерминированный
    случай.
  - Если транзакции **перекрываются**, serializable-изоляция PostgreSQL может
    упорядочить их в любую валидную последовательность. Допустимы оба исхода:
    `200` (restore упорядочен раньше отзыва — страница становится живой, отзыв
    применяется после) и `403` (отзыв упорядочен раньше). Исход не определяется
    тем, чей коммит раньше по wall-clock.
  - Частичного применения нет: транзакция атомарна — либо снят `deletedAt`
    (`200`), либо нет (`403`). Тест на перекрытие проверяет принадлежность
    исхода множеству `{200, 403}` и отсутствие смешанного состояния, а не один
    жёсткий исход; отдельный тест проверяет обязательный `403` при старте
    restore после коммита отзыва.
  - Это утверждение — только про restore; другие эндпоинты в объём #156 не
    входят и не переопределяются.

## Тесты: приёмка и гонки

Тесты — `apps/api` Jest, чёрный ящик на HTTP. **Гоночные тесты выполняются на
реальной PostgreSQL** (e2e-контур), не на моках: предмет проверки — поведение
при serializable-изоляции, мок его не воспроизводит.

**Приёмка (семантика):**

- list возвращает только удалённые страницы запрошенного живого проекта,
  плоско, на любой глубине; точный набор полей `TrashPage`; `content`
  отсутствует.
- Порядок `deletedAt DESC, id ASC`; keyset-пагинация эквивалентна выдаче без
  cursor; `nextCursor` = `null` в конце; `limit`/`cursor` по границам и
  ошибки `400`.
- Изоляция проекта: участник двух проектов видит только страницы из пути.
- restore одной страницы: `deletedAt` снят, дети остались удалёнными, предки
  не восстановлены, `parentId`/`projectId` не изменены, позиция — append,
  `content`/`title`/`editorMode`/Yjs-снапшот/`CalendarEntry` сохранены; ответ —
  обычный `Page` DTO.
- Ошибки: `401`, `403` (нет членства / недостаточная роль), `404` (проект/страница
  нет, проект удалён, страница живая), `409` (предок удалён; дерево изменилось —
  глубина с восстановленной страницей превысила бы 10), `400` (параметры list).
- restore ребёнка под родителем на глубине 10: цепочка предков жива, но возврат
  сделал бы глубину 11 → `409 CONFLICT`, страница остаётся удалённой.

**Гонки (реальная БД):**

| Сценарий                                         | Ожидание                                                                                                                                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| create под родителем параллельно delete родителя | I1 держится: живого ребёнка под удалённым родителем нет                                                                                                                  |
| restore параллельно delete родителя              | Либо `409`, либо каскадный delete; I1 держится                                                                                                                           |
| restore параллельно delete самой страницы        | Линеаризуемый итог; I1 держится                                                                                                                                          |
| restore параллельно move страницы/родителя       | I1 держится; цикл не создаётся                                                                                                                                           |
| два параллельных restore одной страницы          | Ровно один переводит в live; второй → `404`                                                                                                                              |
| отзыв членства перекрывается с restore           | По валидному последовательному порядку: restore раньше — `200`, страница живая; отзыв раньше — `403`, страница удалённая. Оба исхода допустимы; частичного состояния нет |
| restore стартует после коммита отзыва            | Безусловно `403` (снапшот видит отзыв), страница остаётся удалённой                                                                                                      |

## Взаимодействия

- `@noto/shared` — ts-rest-контракт, Zod-схемы `trashPageSchema`,
  `trashResponseSchema` ([ADR-012](../../../../docs/adr/012-api-contract.md));
  публичный `Page` для restore переиспользуется.
- `@noto/api` — контроллер + `ProjectAccessGuard`/`@RequireProjectRole`;
  для restore — отдельная deleted-aware резолюция проекта из страницы; доступ
  наследуется от проекта ([ADR-011](../../../../docs/adr/011-authorization-acl.md)).
- `@noto/api` `PagesService` — общий serializable-протокол с delete/move;
  create приводится в тот же протокол — обязательная часть #156 (см. «Гонки»).
- Prisma: используется существующее поле `Page.deletedAt` и связи
  `PageCollabState`/`CalendarEntry`; новых полей нет.
- Frontend — TanStack Query, корзина в матрице состояния
  ([ADR-005](../../../../docs/adr/005-state-management.md)); вне этой задачи.

## Решения

- **Restore — ровно одна страница.** Дети остаются удалёнными, предки не
  восстанавливаются, перепривязки нет. Единственный способ вернуть поддерево —
  последовательно восстановить предка, затем каждого ребёнка (после
  восстановления предка ребёнок снова доступен для restore).
- **Restore — плоский item-роут** (`/pages/:pageId/restore`), а корзина —
  коллекция в проекте (`/projects/:projectId/trash/pages`): согласовано с
  формой роутов в [pages.spec.md](./pages.spec.md).
- **Существование (404) раньше прав (403).** Для restore удалённая страница
  считается существующей, поэтому не участник получает `403`, а не `404`; это
  конвенция [ADR-011](../../../../docs/adr/011-authorization-acl.md), новые
  классы утечки не вводим.
- **Deleted-aware авторизация не ослабляет существующие guard'ы:** текущая
  семантика остальных item-роутов не меняется.
- **`409 CONFLICT` restore — только «дерево непригодно для возврата».** Ровно
  два случая: предок не жив, либо актуальная глубина с восстановленной
  страницей превысила бы лимит 10 (предка переместили, пока страница лежала в
  корзине). Другие семантики (`409` create идемпотентности, `409` PUT CAS в
  calendar) не смешиваются с restore.
- **Позиция — append, не сохранение исходной.** Исходная `position` могла
  устареть/пересечься; append детерминирован и совпадает с `nextPosition`.
- **Пагинация — keyset, не снапшот.** Консистентного снимка и
  read-your-writes по страницам не обещаем; обещаем детерминированный порядок.
- **Исторические строки не мигрируем.** Схема не меняется. Если в существующих
  данных из-за гонки create/delete уже есть живой ребёнок под удалённым
  родителем, эта задача его не чинит; починка — отдельно. I1 —
  операционная гарантия: она держится для состояний, валидных на входе, после
  исправления create (обязательная часть #156, см. «Гонки»).
- **Исправление create — обязательная часть #156.** Оба пути create (append и
  явная позиция) валидируют родителя/глубину и пишут **в одной**
  serializable-транзакции; отдельной задачей не выносится — иначе I1 не
  держится.
- Лимиты `limit` (default 50, max 100) — предохранитель, пересматриваемые.

## Решение человека (подтверждено для #156)

Пункты подтверждены человеком до перехода к тестам и коду
([ADR-013](../../../../docs/adr/013-spec-driven-development.md),
«spec ревьюят перед стартом»).

- [x] **Single-page semantics:** restore восстанавливает ровно одну страницу;
      дети остаются удалёнными; предки не восстанавливаются; reparent
      запрещён; `parentId` при восстановлении должен быть полностью живым, а
      глубина с восстановленной страницей ≤ 10 (иначе `409`). Подтвердить или
      отклонить.
- [x] **Повтор restore живой страницы = `404`** (не идемпотентный `200`).
- [x] **Не участник на restore удалённой страницы = `403`** (existence раньше
      прав), а не маскирующий `404`.
- [x] **Числа пагинации:** default `limit = 50`, max `100`.
- [x] **Revocation-перепроверка** только для restore; другие эндпоинты не
      трогаем.

## Открытые вопросы

1. **Историческая согласованность I1 (residual).** Есть ли в текущей БД живые
   дети под удалёнными родителями из-за гонки create/delete? Проверка —
   отдельным запросом/задачей; миграция данных в объём #156 не входит.
2. **Индекс под keyset.** `@@index([projectId])` есть; составной
