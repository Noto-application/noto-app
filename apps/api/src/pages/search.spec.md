# Spec: Поиск страниц по заголовкам

**Статус:** Draft
**Дата:** 2026-10-23
**Связанные:** [ADR-011](../../../../docs/adr/011-authorization-acl.md), [ADR-012](../../../../docs/adr/012-api-contract.md), [ADR-013](../../../../docs/adr/013-spec-driven-development.md), [pages.spec.md](./pages.spec.md), [trash.spec.md](./trash.spec.md), #157 (API), #129 (frontend)

## Цель

Дать авторизованному пользователю возможность находить страницы по заголовку
в выбранном проекте или во всех проектах, где у него есть действующее членство.
Результат содержит только данные, необходимые для показа результата и перехода
на страницу.

## Вне scope

- Поиск по содержимому Page, REST content или Yjs-состоянию.
- Полнотекстовый/fuzzy-поиск, подсветка, история запросов.
- Публичные и опубликованные страницы как отдельный источник доступа.
- UI, глобальная командная палитра, поисковый движок и отдельная поисковая
  инфраструктура.

## Контракт

Контракт задаёт API для frontend-задачи #129 и реализуется в `@noto/shared`
(ts-rest + Zod, источник типов и runtime согласно
[ADR-012](../../../../docs/adr/012-api-contract.md)); ошибки используют общий
shape `{ code, message, details? }`.

| Метод | Путь                                     | Кто                 | Успех                           |
| ----- | ---------------------------------------- | ------------------- | ------------------------------- |
| GET   | `/pages/search?q&projectId&limit&cursor` | авторизованный user | `200 { results[], nextCursor }` |

Поля query:

| Поле        | Тип      | Правило                                                    |
| ----------- | -------- | ---------------------------------------------------------- |
| `q`         | `string` | Обязательное; trim, после trim длина 1..200                |
| `projectId` | `uuid`   | Необязательное; ограничивает результаты одним проектом     |
| `limit`     | `int`    | Необязательное; по умолчанию 20, допустимый диапазон 1..50 |
| `cursor`    | `string` | Необязательный непрозрачный курсор предыдущей страницы     |

Пробелы по краям `q` удаляются; внутренние пробелы сохраняются. Запрос только
из пробелов после trim невалиден (`400 VALIDATION_ERROR`). Ввод длиной более
200 символов после trim также возвращает `400`; пустые запросы frontend не
отправляет. Длина ограничивается тем же максимумом, что и заголовок Page.

**Форма результата** (`PageSearchResult`, отдельная компактная схема):

| Поле          | Тип             | Заметка                         |
| ------------- | --------------- | ------------------------------- |
| `pageId`      | `string` (uuid) | Идентификатор страницы для URL  |
| `title`       | `string`        | Текущий заголовок страницы      |
| `projectId`   | `string` (uuid) | Идентификатор проекта           |
| `projectName` | `string`        | Название проекта для результата |

`content`, `editorMode`, `parentId`, Yjs state и пользовательские данные в
ответ не входят. `totalCount` не возвращается.

Успех: `200 { results: PageSearchResult[], nextCursor: string | null }`.
Пустой результат — `results: []`, `nextCursor: null`. Коды ошибок: `401`
`UNAUTHORIZED`, `403` `FORBIDDEN`, `404` `NOT_FOUND`, `400`
`VALIDATION_ERROR`; новые коды не вводятся.

## Поведение

### Поиск

- Ищется только подстрока в `Page.title`, без учёта регистра, включая
  кириллицу. Поиск буквальный: `%`, `_`, `\` и другие специальные символы
  пользовательского ввода не становятся SQL-фрагментами или шаблонами wildcard.
  Внутренняя реализация должна использовать параметризованное значение и
  сохранять буквальную семантику символов шаблона.
- Кроме trim, запрос не нормализуется и не разбивается на слова. Например,
  внутренние пробелы являются частью подстроки.
- Сопоставление выполняется с учётом case-insensitive поведения PostgreSQL в
  поддерживаемой конфигурации; unit/e2e проверки фиксируют регистр и кириллицу.
- Порядок: `title ASC, pageId ASC`. Уникальный `pageId` — tie-breaker при
  одинаковых заголовках; в рамках одного запроса порядок воспроизводим.

### ACL и жизненный цикл

- Эндпоинт требует JWT. Права на чтение проверяются как часть запроса выдачи,
  а не постфильтрацией результата:
  - без `projectId` выбираются только страницы проектов, где существует
    `ProjectMember` текущего пользователя;
  - с `projectId` результат дополнительно ограничивается этим проектом и
    действующим членством текущего пользователя.
- `owner`, `editor` и `viewer` имеют одинаковое право искать и читать
  заголовки. Public/published не даёт доступа к проектам без членства.
- При явно указанном `projectId` отсутствующий или soft-deleted проект
  возвращает `404`; существующий проект без членства пользователя — `403`
  согласно конвенции [ADR-011](../../../../docs/adr/011-authorization-acl.md).
  Проверка доступа не возвращает страницы проекта.
- Исключаются soft-deleted страницы и страницы soft-deleted проектов.
- Результат ограничен доступными проектами до сортировки и пагинации.
  Никакие totals, cursors или ошибки не сообщают о количестве/наличии
  недоступных страниц.
- Отзыв членства, завершённый до выполнения запроса выдачи, исключает проект
  из результата. Как и у других обычных чтений, поиск не является
  транзакционным снимком через несколько запросов.

### Пагинация и конкурентные изменения

- Keyset-пагинация по `(title, pageId)` с сортировкой `title ASC, pageId ASC`.
  Запрос выбирает максимум `limit + 1` строк, чтобы определить наличие
  следующей порции. Полный count не вычисляется.
- `nextCursor` — непрозрачное клиенту значение; клиент возвращает его без
  разбора. Курсор применяется только вместе с исходными нормализованными `q`
  и `projectId`; несовместимый, повреждённый или некорректный курсор даёт
  `400 VALIDATION_ERROR`. Отсутствие следующей порции обозначается `null`.
- ACL, проектный фильтр и фильтры жизненного цикла должны применяться до
  `limit + 1` и к каждой порции. Подмена курсора или его повторное применение
  к другому запросу не может обойти ACL или раскрыть чужую запись.
- Пагинация не является снапшотом. Переименование/удаление страницы,
  изменение членства или состава проектов между запросами может изменить
  последующие результаты; пропуски или повторы при изменении сортировочных
  данных не исключены. Гарантируются только детерминированная сортировка и
  keyset-переход для неизменившихся данных.

## Реализация и границы модулей

- Это операция чтения существующего домена Pages. Следовать корзине: добавить
  контракт/схемы поиска в `@noto/shared`, endpoint в существующий
  `pagesContract`/`PagesController` и метод выборки в `PagesService`.
- Отдельный `PageSearchService` не вводить: отдельного жизненного цикла,
  хранилища или внешней интеграции у поиска нет. При появлении независимого
  поискового backend границу можно пересмотреть отдельно.
- Запрос к БД должен проецировать только четыре поля результата. Не загружать
  Page content или `PageCollabState`.
- Перед добавлением индекса проверить план запроса (`EXPLAIN ANALYZE`) на
  репрезентативных данных и зафиксировать обоснование. Для поиска-подстроки
  не считать обычный B-tree индекс достаточным без подтверждения планом.
  Индекс и миграция добавляются только если измерения показывают необходимость;
  внешний поисковый движок не требуется.
- Документация API и экспорт типов/схем в `@noto/shared` обновляются вместе
  с контрактом.

## Проверка и приёмка

- Контракт/Zod: query trim, пустой/пробельный/слишком длинный запрос,
  недопустимый `projectId`, лимит по умолчанию, границы лимита, битый и
  привязанный к другому запросу cursor.
- Интеграционные проверки на PostgreSQL: регистр, кириллица, внутренние
  пробелы, `%`, `_`, `\`, совпадения/отсутствие совпадений.
- ACL и отсутствие утечек: все три роли, outsider при явном `projectId`,
  запрос без `projectId` для участника нескольких проектов, пользователя без
  членств, удалённый проект и удалённая страница.
- Пагинация: лимит не превышен, нет повторов и пропусков на неизменившемся
  наборе, одинаковые заголовки, корректный последний cursor, cursor не
  переносит доступ из одного проекта/запроса в другой.
- Проверить план на репрезентативных данных; вывод и решение об индексе
  включить в review реализации. Тесты доступа и отсутствия утечки выполняются
  на реальной БД, не только на моках.
- Frontend #129 использует этот контракт как потребитель; его готовность не
  является предусловием реализации API. Тесты проходят человеческое ревью до
  написания реализации согласно
  [ADR-013](../../../../docs/adr/013-spec-driven-development.md).
