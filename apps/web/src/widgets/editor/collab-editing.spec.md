# Spec: Yjs ↔ BlockNote collaborative editing

**Статус:** Draft
**Автор:** Stas Kobles
**Дата:** 2026-09-10
**Связанные:** [ADR-005](../../../../../docs/adr/005-state-management.md), [ADR-006](../../../../../docs/adr/006-realtime.md), [RFC-002](../../../../../docs/rfc/002-rich-text-editor.md), [RFC-003](../../../../../docs/rfc/003-yjs-provider.md), issue #110, зависит от #108 (auth-hook, слит) и #109 (persistence)

## Цель

Редактор страницы работает поверх общего Yjs-документа: правки одного клиента
видны у другого в реальном времени, через уже поднятый Hocuspocus-сервер
(#108) с авторизацией по access-cookie.

## Вне scope

- Presence-курсоры и комментарии (Socket.io, отдельная задача).
- Офлайн-очередь правок (при уходе со страницы в оффлайне несинхронизированные
  правки теряются — см. Крайние случаи).
- Миграция существующего REST-контента страниц в Yjs — отдельная задача.
  Поэтому collab-режим **не включается** на страницах с уже сохранённым
  REST-контентом (см. «Критерий включения»).
- Durable-хранение Yjs-состояния — это #109 (persistence). **Пользовательское**
  включение collab зависит от #109 (см. «Критерий включения»); без неё документ
  не переживает рестарт сервера.

## Критерий включения (feature-flag)

Задача разбита на два уровня готовности, чтобы не отдать пользователям режим,
теряющий контент:

1. **Локальный спайк (этот PR).** Collab-режим за флагом
   `NEXT_PUBLIC_COLLAB_ENABLED`, по умолчанию **выключен**. При выключенном
   флаге редактор работает по-прежнему (REST + автосейв) — существующие
   страницы не затрагиваются. Спайк гоняем локально на **новых/тестовых**
   страницах (пустой контент).
2. **Включение пользователям.** Разрешено **только** при одновременно:
   - выполненной #109 (persistence) + проверке восстановления документа после
     рестарта сервера;
   - **durable per-page признаке режима**: страница, однажды переведённая в
     collab, помечается персистентно (например `page.editorMode = 'collab'`
     или наличие Yjs-снапшота из #109) и **всегда** открывается через Yjs,
     независимо от флага. Флаг `NEXT_PUBLIC_COLLAB_ENABLED` управляет **только**
     переводом **новых** страниц в collab, а не открытием уже-collab страниц.

   Почему обязательно: без per-page признака выключение флага (или эвристика
   «пустой REST-контent») откроет уже-Yjs страницу через REST → пустой редактор
   поверх контента, который живёт в Yjs. Эвристика «пустой REST-`content`» —
   **только для локального спайка** на тестовых страницах.

Пока миграция REST→Yjs не сделана, перевод ограничен страницами без
REST-контента; страницы со старым REST-контентом остаются на REST-редакторе.

## Контракт

**Провайдер:**
`HocuspocusProvider({ url, name, document })`
- `url` — WebSocket единого origin: `ws(s)://<host>/collab` (тот же хост, что
  и приложение; в dev через Caddy `:8080` → collab `:5555`). HttpOnly
  access-cookie уходит на хендшейк сама (единый origin, #108).
- `name` = **голый `pageId`** (UUID без префикса) — совпадает с
  `documentName` в контракте авторизации #108.
- `document` — экземпляр `Y.Doc`, живёт на время открытия страницы.

**Редактор:**
`useCreateBlockNote({ collaboration: { provider, fragment, user } })`
- `fragment` — `doc.getXmlFragment('document-store')` (общий фрагмент BlockNote).
- `user` — `{ name, color }` для CRDT-меток (минимально; курсоры — вне scope).
- В collab-режиме `initialContent` **не передаётся** (контент приходит из Yjs).

**Компонент `PageEditor`:** пропсы прежние (`pageId`, `content`). Выбирает
режим:
- **Спайк (этот PR):** collab включается, если флаг `NEXT_PUBLIC_COLLAB_ENABLED`
  поднят **и** REST-`content` пуст (новая/тестовая страница).
- **Пользовательский режим (после #109):** страница с durable-признаком collab
  открывается через Yjs **всегда**; флаг решает только, создавать ли **новую**
  страницу в collab. Открытие уже-collab страницы от флага не зависит.

Иначе — прежний REST-редактор без изменений. В collab-режиме `content` из REST
для инициализации не используется (контент из Yjs).

## Поведение

1. Открытие `/app/[pageId]` при активном collab-режиме (режим выбран по
   разделу «Контракт» → `PageEditor`) → создаём `Y.Doc` + `HocuspocusProvider`
   на `pageId`. Иначе — прежний REST-редактор.
2. Хендшейк: сервер (#108) проверяет access-cookie и членство в проекте.
   Успех → провайдер синхронизирует док.
3. BlockNote привязан к фрагменту → правки применяются к `Y.Doc` и
   транслируются другим клиентам в реальном времени.
4. `provider.on('synced')` → снимаем индикатор загрузки, редактор доступен.
5. Смена `pageId` / размонтирование → `provider.destroy()` и уничтожение
   `Y.Doc` (без утечек соединений).

## Крайние случаи

- **Отказ авторизации на хендшейке** (нет cookie / не участник / чужая
  страница) → провайдер не синкается. Показать состояние «нет доступа /
  ошибка соединения», не белый экран. Оборачиваем в существующий
  `ErrorBoundary` редактора.
- **Разрыв WS (остаёмся на странице)** → Hocuspocus сам реконнектит; индикатор
  показывает «переподключение». Правки копятся в локальном `Y.Doc` и сливаются
  после реконнекта — **только пока жив редактор** (обещание слияния ограничено
  временем жизни `Y.Doc`).
- **Уход со страницы с несинхронизированными правками** → при смене `pageId` /
  размонтировании `Y.Doc` уничтожается; если синк не завершён (оффлайн/разрыв),
  локальные несинхронизированные правки **теряются** (офлайн-очередь вне scope).
  Смягчение: пока провайдер не в `synced`, показываем явный статус
  «не сохранено»; при уходе/закрытии вкладки в этом состоянии — best-effort
  `beforeunload`-предупреждение. Гарантий сохранения оффлайн-правок не даём.
- **Пустой документ** (новая страница) → BlockNote создаёт один пустой блок
  поверх пустого фрагмента.
- **Гонка двух клиентов** → разрешается CRDT (Yjs), спец-логики не пишем.

## Взаимодействия

- **Слои (ADR-005):** контент редактора при collab — **только Yjs**, не
  дублируем в TanStack Query / Zustand. `pageId` — из URL.
- **REST-автосейв (`use-page-autosave.ts`):** в collab-режиме **отключается** —
  иначе двойная запись контента (Yjs + REST PATCH) конфликтует с ADR-005.
  Durability берёт на себя серверный persistence (#109). До #109 контент
  живёт только в памяти сервера.
- **Метаданные страницы** (title и пр.) — по-прежнему REST/Query; в Yjs идёт
  только тело документа.
- **Сервер:** Hocuspocus (#108) — WS `/collab`, авторизация по токену.

## Тестирование

ADR-013: CRDT/realtime идёт **спайком**, но не «без тестов» — автотесты
добавляются **после** спайка (интеграционные, на завязку провайдер↔редактор и
статусы синка), realtime-взаимодействие двух клиентов остаётся ручным.

Спайк (ручная проверка, ожидаемый результат):
1. Два клиента открыли одну страницу → правка в клиенте A появляется у B за
   ~секунду.
2. Одновременная правка в A и B в разных местах → оба текста сохранены (CRDT не
   теряет и не дублирует).
3. Разрыв сети у A (на странице), правка, восстановление → правка долетает до B
   после реконнекта.
4. Отказ авторизации (не участник проекта) → редактор не синкается, показан
   статус ошибки, не белый экран.
5. (После #109) правка → рестарт collab-сервера → повторное открытие страницы
   показывает сохранённый контент.

Интеграционные автотесты после спайка (Vitest): выбор режима по флагу/пригодности
страницы, маппинг событий провайдера в статусы индикатора (`syncing`/`synced`/
`disconnected`), отключение REST-автосейва в collab-режиме. Реальный WS/CRDT в
этих тестах мокается.

## Открытые вопросы

- Индикатор соединения/синка: свой минимальный компонент или переиспользовать
  `AutosaveIndicator` под новые состояния (`syncing` / `synced` /
  `disconnected`)? — решить на спайке.
- Источник `user.name`/`color` для CRDT-меток до появления presence — брать из
  `auth/me` (имя) + детерминированный цвет по userId?
- Формат ws-URL: выводить из `window.location.origin` или отдельный
  `NEXT_PUBLIC_COLLAB_URL`? (единый origin делает первое достаточным).
- Механизм durable per-page признака collab для пользовательского режима:
  колонка `page.editorMode` или наличие Yjs-снапшота из #109? (на спайке — по
  пустому REST-`content`; для включения — решить вместе с #109).
