## Цель

Пользователь видит страницы проекта в месячной сетке, открывает их, создаёт
страницу на день, переносит и снимает дату, а также встраивает календарь
блоком в редактор. Модель, API, ACL и жизненный цикл — в
[API-спеке](../../../../../apps/api/src/calendar/calendar.spec.md); здесь —
URL, состояние, представление и блок.

## Контракт

### URL и навигация

Экран: `/app/calendar?projectId=<uuid>&month=YYYY-MM`. Проект и месяц — только
в URL ([ADR-002](../../../../../docs/adr/002-routing-and-domains.md),
[ADR-005](../../../../../docs/adr/005-state-management.md)).

- Переход из сайдбара с открытой страницы несёт её `projectId`.
- Нет `projectId` в прямой ссылке: после загрузки доступных проектов —
  канонический `router.replace` на первый доступный проект в серверном
  порядке, видимо выбранный; нет проектов → empty state «нет проекта».
- Нет `month`: текущий локальный календарный месяц и канонический `replace`.
- Невалидный синтаксис `projectId` или `month`: состояние «невалидная ссылка»,
  запрос не отправляется, есть действие к каноническому доступному
  проекту/текущему месяцу.
- Синтаксически валидный, но недоступный: `403` → forbidden, `404` → проект
  недоступен; молчаливого fallback нет.
- Прямая валидная ссылка работает.
- Будущий переключатель проекта использует URL и в v1 может оставаться
  выключенным; смена проекта сохраняет валидный месяц, закрывает/сбрасывает
  формы и делает `push` URL.
- prev/next/today делают `push` URL; back/forward рендерят состояние
  исключительно из URL.
- Формы захватывают контекст проекта; при смене контекста отменяются/сбрасываются;
  submit отказывает при устаревшем контексте.

### Состояние (матрица [ADR-005](../../../../../docs/adr/005-state-management.md))

| Слой            | Что хранит                                     |

### Query keys и инвалидация

Ключи с префиксом по проекту, точным `[from, to)` или текущей Page:

```ts
calendarEntryKeys.project(projectId); // ['calendar-entry', projectId]
calendarEntryKeys.range(projectId, from, to); // [...calendarEntryKeys.project(projectId), 'range', from, to]
calendarEntryKeys.page(projectId, pageId); // [...calendarEntryKeys.project(projectId), 'page', pageId] — #136
```

- `from`/`to` — не календарные 28–31 день месяца, а фактически видимая
  месячная сетка: от первого дня недели первой строки до последнего дня
  недели последней строки включительно. Сетка занимает до 6 недель и
  **включает дни соседних месяцев**; карточки этих соседних дней приходят из
  того же ответа `[from, to)`, без отдельного запроса. Формулировка «записи за
  месяц» ниже означает именно видимую сетку, а не только календарный месяц.
- Мутации инвалидируют календарный префикс проекта: все диапазоны и точечные
  чтения, включая открытые формы и будущий блок #137.
- create дополнительно инвалидирует список/дерево страниц и detail новой Page.
- assign/change/remove обновляют диапазоны записей и релевантный detail/list
  затронутой Page.
- Переименование Page инвалидирует префикс проекта, чтобы обновился заголовок.
  В #136 календарная инвалидация добавлена и в существующий title autosave.
- Мутация и её поздние callbacks используют захваченные идентификаторы
  исходного проекта/Page, не текущий URL. После смены контекста ответ может
  обновить/инвалидировать исходные кэши, но не навигирует, не показывает успех
  в новом контексте и не отправляет автоматически новые записи/retry.
  После закрытия исходной формы это действует и без смены проекта/Page:
  поздний ответ не навигирует, не показывает success toast и не меняет
  состояние вновь открытой формы в том же контексте; допустимы только
  обновление/инвалидация захваченных исходных кэшей.

Спека фиксирует наблюдаемый результат, а не механику (optimistic/refetch).

### Обновление на клиенте

Для календарных диапазонов переопределяем текущие дефолты: refetch при
возврате фокуса окна и переподключении, плюс polling раз в 60 секунд, только
пока компонент смонтирован и документ видим. Данные «eventual» — realtime не
обещаем. Интервал 60 секунд принят (бывший открытый вопрос №2).

Ошибка без загруженных данных блокирует сетку; при временной сетевой/5xx-ошибке
фонового refetch сохранённые данные (включая пустой список) и сетка остаются
видимыми с неблокирующим предупреждением «Не удалось обновить календарь» и
retry; ответы `401`/`403`/`404` скрывают сетку и карточки даже при наличии кэша.

### Роль пользователя

Серверное обязательное `Project.currentUserRole` (`owner | editor | viewer`)
уже объявлено в `projectSchema`; prerequisite роли принят до #136.
#135 — исторически строго read-only для всех
пользователей: сетка, карточки, навигация и состояния чтения, без мутационных
контролов и без индикации роли. Для #135 поле роли не требуется.

Поле серверно-вычисляемое для запрашивающего; отдельная prerequisite-задача
**до #136, не до #135**, вне #134/#135 выполнена (бывший открытый вопрос №1).
В #136 UI выводит мутационные аффордансы только из этого авторитетного поля;
дубля capabilities нет. Неизвестная/отсутствующая роль никогда не разрешает
запись. Никогда не выводим роль из Page, отсутствия данных или пробного
запроса/`403`. Backend ACL не меняется: read-only UI не доказывает серверные
права viewer или запрет доступа постороннему.

### Действие в TopbarMenu текущей Page

На экране Page (`/app/[pageId]`) `TopbarMenu` текущей Page даёт действие
«Назначить дату», когда у Page нет даты; когда дата есть — смену и снятие
даты. Действие доступно и для вложенной Page: назначение/смена/снятие
сохраняет её `parentId` и структуру дерева. Это та же мутация
assign/change/remove (существующий PUT), что и из формы карточки календаря.
Мутационный контракт не меняется, но для чтения требуется **новый точечный GET
из расширения #136** в API-спеке, сверх #134. Правила кэша и инвалидации — выше.
Аффорданс виден только `owner`/`editor`; `viewer` его не видит.
Действие реализовано в #136 вместо заглушки `TopbarMenu`; точное представление
формы — деталь реализации, не новый доменный контракт.

Для текущих `projectId`/`pageId` точечный GET различает проверенное отсутствие
записи (`200 { entry: null }`) и неизвестное состояние (до успеха чтения,
loading/error). Отсутствие Page в диапазоне или пустой кэш **не** означают
отсутствие даты: запросы всех месяцев не перебираются, лимит list ≤42 дней
сохраняется, в Page DTO календарное поле не добавляется. При неизвестном
состоянии форма не предлагает назначение как будто даты нет и не отправляет PUT;
ошибка чтения даёт retry, не probing-запись. `401`/`403`/`404` не превращаются
в `null` и скрывают недоступные данные/действия.

После успешного чтения `expectedDate` для PUT берётся из прочитанной записи,
либо `null` из успешного nullable-ответа. При неопределённом сетевом результате
PUT повтор отправляет тот же захваченный `{ date, expectedDate }` в том же
контексте при разрешающей роли Project: desired-state no-op сохраняет
идемпотентность, молча подменять `expectedDate` нельзя.
`409` PUT требует точечного GET: если свежая дата уже равна целевой (включая
`null`), цель достигнута, новый PUT не нужен; это не доказывает, что изменение
сделал именно наш запрос. Иначе показывается конфликт, новая попытка требует
явного подтверждения пользователя и только тогда нового `expectedDate` из
прочитанного состояния. Неудавшееся чтение оставляет конфликт неразрешённым;
автоматического overwrite/retry с новым `expectedDate` нет.
`409` create не трактуется как CAS и не запускает create с новым ключом.

### Намерение create и неопределённый результат (#136)

- До первой отправки валидируются/нормализуются `title` (trim, правила Page) и
  date-only `date`, один раз создаётся UUID `clientRequestId`. Захватывается
  неизменный снимок `{ projectId, title, date, clientRequestId }`.
- Пока запрос выполняется, повторная отправка и редактирование снимка запрещены.
- Первый достоверный `400`/`401`/`403`/`404`, если ранее не было неопределённого
  результата, означает известный отказ: показать ошибку. Пользователь может
  явно отредактировать форму как новое намерение после проверки актуального
  контекста и разрешающей роли Project; ошибка сама не создаёт новый UUID
  и не запускает новую отправку.
- Потеря сети/timeout, любой `5xx`, неизвестный или утраченный HTTP-статус,
  а также `2xx` с невалидным телом успеха означают неопределённый результат:
  ответ мог потеряться после коммита. Форма сохраняет снимок и ключ,
  блокирует поля и показывает ошибку с retry. Признак ранее неопределённого
  результата (`priorUnknown`) сохраняется до проверенного `201`/replay `200`
  либо до закрытия/сброса формы по ограниченной политике ниже.
- После неопределённого результата **любой последующий `400`/`401`/`403`/`404`**
  не доказывает, что исходный create ничего не создал: снимок/ключ остаются
  замороженными, `priorUnknown` не сбрасывается. Неизвестная/запрещающая роль
  блокирует retry, но не разрешает неопределённость. Retry доступен только
  в той же открытой форме, при совпадении актуального контекста с захваченным
  и разрешающей роли Project; он отправляет **тот же** проект, payload и ключ.
  Новый UUID после возможно успешного create не минтится.
- `409` create — конфликт fingerprint ключа: сохраняются исходное намерение
  и признак `priorUnknown`, если он был. Новый UUID автоматически не создаётся;
  логика разрешения CAS-конфликта PUT здесь не применяется.
- Только проверенные `201` и replay `200` завершают намерение как успешное,
  закрывают ещё актуальную исходную форму и обновляют кэши.
  Replay возвращает текущее состояние; `entry: null` допустим, исходная дата
  не воссоздаётся клиентом. Ошибка последующей инвалидации/refetch кэша —
  отдельная ошибка обновления после известного успеха POST, а не неопределённый
  create: она не запускает повторное создание.
- Классификация исхода календарной мутации сохраняет HTTP-статус и валидность
  ответа **до** проекции в `toApiClientError`: существующий `ApiClientError`
  статуса не хранит, а невалидное тело ошибки превращается в `VALIDATION_ERROR`.
  По одному `code` нельзя заключать, что create точно отклонён; утраченный
  статус трактуется консервативно как неопределённость. Это локальное требование
  календарного адаптера, не изменение общего shape ошибок или auth-клиента.
- Форму можно закрыть. При пользовательском закрытии или смене контекста
  во время pending или с неопределённым результатом показывается предупреждение
  «Результат неизвестен: проверьте
  созданные страницы перед новым намерением». Форма закрывается/сбрасывается,
  прежний retry больше недоступен, новая форма — новое намерение с новым ключом.
  Гарантия retry без дубля ограничена **той же открытой формой**: между
  закрытием и новым открытием дубли не исключены. Глобального хранения,
  Zustand для намерения и сохранения между перезагрузками нет.
- Смена контекста запрещает stale submit/retry; уже отправленный запрос может
  завершиться и инвалидировать захваченный исходный проект. Это не отмена
  серверного коммита и не разрешение отправлять запись в старый проект после
  переключения; правила поздних callbacks — из раздела инвалидации, в том числе
  после закрытия и нового открытия формы в том же контексте.
- Предупреждение гарантируется только для пользовательского закрытия формы
  и смены контекста внутри приложения, не для browser reload или auth redirect.
  Существующий auth-клиент при `401` может выполнить refresh/retry, а при
  неудаче перейти на `/login` через `window.location.assign`; это поведение
  не блокируется и не меняется. Между перезагрузками/редиректом намерение
  не сохраняется, гарантия retry за эти границы не распространяется.

### Блок календаря в редакторе

- Обязательный v1: пункт slash menu.
- Проект берётся из содержащей Page, никогда не сохраняется пропом.
- Персистим только тип блока и минимальные структурные/версионные пропсы,
  если их требует BlockNote: **без** `projectId`, записей, заголовков,
  query-кэша, месяца.
- Данные и формы те же; viewer — read-only; карточки ведут на `/app/[pageId]`.
- Месяц локален для каждого инстанса; навигация не порождает транзакцию
  документа/undo/Yjs. Несколько блоков делят записи/кэш Query, но месяц
  независим. Удаление блока удаляет только блок.
- REST `editor.document` и collab `Y.XmlFragment` должны roundtrip-ить один
  тип через одно определение схемы; #131 — OPEN и не prerequisite для
  написания спеки, но #133 обязан проверить на durable-пути `editorMode` и
  текущем PR до production. Финальное место адаптера/интеграции здесь не
  утверждается.
- Фокус/клик/формы/узкая колонка: интерактивные контролы не превращаются
  случайно в правку текста или перетаскивание блока; клавиатура и touch
  работают; оверлей формы не пишет в документ редактора; безопасный
  overflow/адаптив ([ADR-014](../../../../../docs/adr/014-responsive-strategy.md)).
- Clipboard: внутреннее копирование блока между Page сохраняет только тип, без
  записей; вставленный блок резолвит проект целевой Page. Внешний HTML/text
  export, публичный/неподдерживаемый/без контекста → статичный безопасный
  placeholder без `projectId`, записей, заголовков и без fetch. #133 проверяет,
  различимы ли эти случаи; если нет — privacy-first fallback: placeholder/inert
  блок, а не сериализация или запрос приватных данных.

### FSD-размещение

- `entities/calendar-entry` — типизированные query/data-контракты и нейтральные
  display-данные записи.
- Мутационные сценарии и формы — в feature-слое, переиспользуемые экраном,
  Topbar и будущим блоком #137; entity содержит общие data/query-контракты,
  а не формы. Черновик и снимок намерения остаются локальными форме.
- Точка входа `TopbarMenu` текущей Page — в `widgets/topbar`; виджет
  импортирует мутационный feature/entities/shared (вниз по слоям), а сценарий
  assign/change/remove остаётся в feature-слое.
- Композиция маршрута/полного экрана — в app/pages/widgets.
- Editor-виджет может импортировать features/entities/shared, но не соседний
  календарный виджет.
- Переиспользуемый календарный UI — ниже обеих интеграций; точное место
  адаптера библиотеки/кастомной BlockNote-интеграции решает #133.
- Циклы срезов одного слоя запрещены.
- Локация этой спеки в entity сама по себе не требует держать всю реализацию
  внутри entity.

### Инварианты

- Заголовок всегда `Page.title`.
- В первом релизе у Page максимум одна календарная дата — одна date-only дата,
  не диапазон: нет `start`/`end`, времени суток и timezone.
- Иерархия Page не влияет на календарные даты: родительская и каждая дочерняя
  Page планируются независимо; перемещение Page не меняет её календарную дату.
- Проект никогда не персистится в блоке.
- Месяц экрана — в URL; месяц блока — локально на инстанс.
- Server state — Query, черновики — RHF/local, UI — Zustand, документ — Yjs.
- `from`/`to` диапазона — видимая месячная сетка (до 6 недель, включая дни
  соседних месяцев), а не только календарные 28–31 день месяца.
- #135 read-only для всех, без мутационных контролов и индикации роли; с #136
  viewer и неизвестная роль не разрешают запись. Права — только из серверного
  `Project.currentUserRole`, не из Page, отсутствия данных или пробного запроса/`403`.
- Placeholder/inert-блок не делает fetch и не несёт приватных данных.
- Календарный доменный контракт не зависит от библиотеки.

## Поведение

В #135 реализуется только чтение для всех: загрузка и состояния, открытие
карточек и URL-навигация. Создание, формы смены/снятия даты и роль-зависимые
аффордансы ниже относятся к #136 после отдельной prerequisite-задачи роли.

1. Экран грузит проекты и (после резолва `projectId`) записи за видимую
   месячную сетку (`[from, to)`, до 6 недель, с днями соседних месяцев).
2. Состояния: loading, empty, error + retry, forbidden, unavailable, invalid
   URL / нет проекта; в #135 весь экран read-only без индикации роли.
3. Клик по дню создаёт Page на дату в корне проекта (`parentId = null`); форма
   заголовка — правила Page. Снимок и `clientRequestId` фиксируются до первой
   отправки; неопределённый результат и retry — по разделу намерения create.
4. Карточка открывает `/app/[pageId]`; форма меняет/снимает дату.
5. `TopbarMenu` текущей Page даёт «Назначить дату» для Page без даты и смену/
   снятие даты для Page с датой; аффорданс только у `owner`/`editor` (#136).
6. prev/next/today меняют `month` в URL; back/forward восстанавливают вид из
   URL.
7. Viewer видит сетку и карточки, но без мутационных аффордансов.

## Критерии приёмки

- Прямая валидная ссылка `/app/calendar?projectId&month` открывает нужный
  проект и месяц.
- prev/next/today и back/forward согласованы с URL.
- #135 — read-only для всех, без мутационных контролов и индикации роли;
  поле `Project.currentUserRole` не prerequisite для этого экрана.
- До #136 выполнена отдельная обязательная prerequisite-задача серверного
  `Project.currentUserRole`; неизвестная/отсутствующая роль не разрешает запись.
- Создание, перенос и снятие даты видны без перезагрузки; Page при снятии
  сохраняется.
- Viewer не видит мутационных аффордансов.
- Реальный доступ viewer и отказ постороннему проверяются на backend/сквозном
  уровне (#134/#139), не считаются доказанными read-only UI или checkbox роли.
- Действие «Назначить дату» и смена/снятие доступны из `TopbarMenu` текущей
  Page для `owner`/`editor` и отсутствуют у `viewer` (#136).
- Даты не зависят от иерархии: назначение/снятие даты не меняет `parentId` и
  структуру дерева, не наследуется потомками и не затрагивает родителя;
  перемещение Page не меняет её дату.
- Несколько блоков на странице не влияют на месяцы друг друга.
- При одинаковых `projectId` и `[from, to)` экран и встроенный блок показывают
  одни и те же записи после принятой политики Query/refetch (общий кэш и
  одинаковые ключи диапазона), включая карточки соседних месяцев.
- В окружениях с разными timezone дата записи не сдвигается.

### Проверки #136 (test-first, одобрены до реализации)

- Entity data/query: точечный GET и ключ `['calendar-entry', projectId, 'page', pageId]`,
  `200 null` отдельно от loading/error; дата вне диапазона не теряется, полный
  scan месяцев и probing-мутации отсутствуют. Инвалидация префикса охватывает
  диапазоны и точечные чтения.
- Общий feature форм: нормализованный снимок и один UUID до отправки;
  pending блокирует поля и double submit; потерянный ответ/timeout, `5xx`,
  неизвестный статус и невалидный `2xx` → замороженные поля и точный retry
  без нового ключа. После неопределённости последующие `400`/`401`/`403`/`404`
  не снимают `priorUnknown` и не разрешают редактирование/новый UUID;
  до неопределённости достоверный отказ позволяет только явно новое намерение
  при валидных роли/контексте. Сохранение статуса до error-проекции проверяется
  отдельно от `code`, включая `500` с невалидным телом.
  Проверенные `201`/replay `200`, в том числе `entry: null`, завершают create;
  ошибка инвалидации после успеха не запускает повторное создание.
  `409` create сохраняет намерение/`priorUnknown`, без нового ключа и PUT-логики.
  Закрытие pending/неопределённого create и смена контекста с предупреждением,
  сброс, новая форма с новым ключом; гарантия не распространяется за закрытие,
  reload/auth redirect, общий auth flow не меняется.
- Assign/change/remove и Topbar: `owner`/`editor` разрешены только по Project,
  viewer/неизвестная роль запрещены; unknown не равен null; `expectedDate`
  из успешного чтения; неопределённый PUT повторяет исходный `{ date, expectedDate }`;
  CAS `409` → точечный refetch: уже целевая дата (включая `null`) → без PUT
  и без утверждения, что изменение наше; иначе новый `expectedDate` только
  после явного подтверждения, неудачный refetch оставляет конфликт неразрешённым;
  date-only, `parentId` и независимые даты родителя/потомков сохраняются.
- Смена контекста: stale submit/retry не отправляется; поздние ответы работают
  с захваченными ключами исходного проекта/Page и не навигируют/не показывают
  успех в новом контексте. После закрытия и нового открытия формы даже в том же
  контексте поздний ответ не меняет новую форму, не навигирует и не показывает
  toast. Запрещающая/неизвестная роль блокирует retry, не снимая неопределённость.
  Общие forms/data доступны будущему блоку без
  межвиджетного импорта и без намерений/server state в Zustand.
- Регрессия title autosave: переименование инвалидирует календарный префикс
  исходного проекта (и диапазоны, и точечные данные), включая поздний ответ
  после смены контекста. Существующая политика polling и обработки ошибок
  диапазона остаётся без изменений.
